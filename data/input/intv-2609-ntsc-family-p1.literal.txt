# Literal controller table of profile intv-2609-ntsc-family-p1 (D-02, D-03; plan 05-01).
#
# Claim tier: source-expectation. This file is a transcription of two cached community sources:
# the ConsoleMods controller-port matrix (SRC-consolemods-intv-pinouts, revision 23186: which
# connector pins each control grounds, plus the pin-to-bit map) and the key-table image of the
# community wiki Hand Controller page (SRC-intv-wiki, Hand_controller.png@oldid-14808: for each
# control the value whose set bits are the bits a press clears). Both are tier 4 and likely one
# lineage, so their agreement is a transcription cross-check, not independent hardware evidence
# (C16). A pass of the input gate step shows that this file is self-consistent and that a
# profile or generated table agrees with it, not that the console behaves this way.
#
# Independence rule: this file is written from the sources only. It is never derived from,
# generated from or edited to match a profile field, a generated table, a core output or a
# planning-note table it judges, and it names no profile field. Where a source and the profile
# differ, this file keeps the source reading and the profile is the side that changes.
# Emulator source code is never a source for a row.
#
# Row grammar (one row per line, single spaces, columns in this order):
#   <NAME> pins=<n,n[,n]> cleared=<HH> wiki=<HH> byte=<HH> src=<SRC-id>@<locator> tag=<tag> conf=C<n>
#   NAME     an IVS_CTRL_ name without the prefix, exactly the set of data/expected/input-bits.ids.
#   pins     the connector pins the control grounds, ascending, from the ConsoleMods matrix.
#   cleared  the eight-bit mask of the bits a press clears: the pins mapped through the pin-to-bit
#            map below, OR-ed together, two uppercase hex digits.
#   wiki     the value printed for the control in the wiki image, read independently of the
#            pins; it must equal cleared (the image rows are in the unchanged hexadecimal form).
#   byte     the byte a read returns with only that control pressed: FF XOR cleared.
#   src      the pin source and the locator of the row (Controller_Matrix-<row>); the wiki value
#            of every row is from SRC-intv-wiki, locator Hand_controller.png@oldid-14808.
#   tag      a source-authority tag of data/tiers.json.
#   conf     a discrepancy id (C16: the matrix is unmeasured and has one lineage).
# Pin-to-bit map (ConsoleMods, controller port table): pin 4 = b0, pin 3 = b1, pin 2 = b2,
# pin 1 = b3, pin 9 = b4, pin 8 = b5, pin 7 = b6, pin 6 = b7 (pin 5 is ground). The table is
# identical for both ports (D-02); which connector feeds which port is C66.
# Disc names: direction 1 of the matrix is the top of the disc in the wiki image and the numbers
# run clockwise (N, NNE, NE, ENE, E, ESE, SE, SSE, S, SSW, SW, WSW, W, WNW, NW, NNW); the compass
# names come from the image only. The two top side buttons read the same code in both sources.
#
# Notes from the wiki prose (SRC-intv-wiki, oldid 14808), all reproduced by the union rule
# byte = FF XOR (OR of the cleared masks of every pressed control):
#   1. Reading an idle controller returns all ones in the low eight bits: FF.
#   2. Pressing key 1 alone clears bits 0 and 7 and reads 7E (row KEY_1).
#   3. Pressing keys 1 and 9 together clears bits 0, 2, 5 and 7 and reads 5A
#      (cleared 81 OR 24 = A5, FF XOR A5 = 5A).
#   4. A single keypad press, and a side button combined with a disc input, can be decoded
#      uniquely (class single-control and disc-side in data/expected/input-policies.ids).
#   5. A keypad press combined with a side button or a disc input, and two side buttons pressed
#      together, cannot be decoded uniquely (classes key-disc, key-side and side-side).

# 31 wiki values; no disagreement was found and none was corrected.
