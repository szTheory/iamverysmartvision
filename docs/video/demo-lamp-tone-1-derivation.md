## (a) Program specification

<!-- blind-spec-begin -->

The program `ivs-demo-lamp-tone-1` ("Lamp Tone") is an original cartridge program entered through the project boot stub, contract 2 (cartridge reset entry `$5000`, cartridge interrupt entry `$5004`, the stub hands every interrupt to `$5004` with the interrupt system disabled), with the zero graphics ROM and profile `intv-2609-ntsc-family-p1`. It makes two rows of eight lamps follow the two controller ports and gives each port one PSG voice. It has no text, no graphics ROM read, no EXEC call, no data table and no moving object, and it never halts.

**A1 Ports.** The scenario words `c0` and `c1` drive the two ports that a guest reads at `$01FE` (`c0`) and `$01FF` (`c1`); the program never names a player. The byte of a port is the low eight bits of the word read; a pressed control clears bits (the controller literal gives each control's byte and the rule that a combination clears the union of the bits), so an idle port reads `FF`.

**A2 Lamps.** Each port has a row of eight lamps. Lamp i, i = 0 to 7 from left to right, shows bit 7 minus i of the port byte and is lit when that bit reads 0 (a cleared bit lights its lamp; nothing is decoded, so an ambiguous combination of controls is shown as the union of its bits). A lit lamp is color index 2 and an unlit lamp is color index 1.

**A3 Display.** The display uses Foreground/Background mode with one project-authored graphics RAM card, card 0, a solid block (its eight pattern bytes `$3800` to `$3807` are all `FF`, so every pixel of the card is foreground). The lamp rows are BACKTAB cells: port 0 occupies row 4, columns 6 to 13, that is addresses `$0256` to `$025D` (lamp i at `$0256` plus i); port 1 occupies row 7, columns 6 to 13, addresses `$0292` to `$0299` (lamp i at `$0292` plus i). An unlit lamp word is `$0801` (graphics RAM card 0, foreground 1) and a lit lamp word is `$0802` (foreground 2); the background field of both is 0. All 16 lamp words are written in every interrupt service routine, whether or not a port changed. Every other BACKTAB word is `$0000` (graphics ROM card 0, foreground 0, background 0; the zero ROM has no image, so such a cell shows color index 0 everywhere). In the delivered plane (159 x 96 positions) lamp i of port 0 covers x = 48 + 8 i to 55 + 8 i, y = 32 to 39, and lamp i of port 1 covers x = 48 + 8 i to 55 + 8 i, y = 56 to 63; the declared lamp rectangles are x = 48 to 111 with y = 32 to 39 (port 0) and y = 56 to 63 (port 1). The border color and the color stack stay at their power-on values (0).

**A4 Memory map of the program.** `$02F0` init marker, `$03C5` once initialization is done; `$02F1` frame counter; `$02F2` port 0 last byte; `$02F3` port 0 change counter; `$02F4` port 1 last byte; `$02F5` port 1 change counter; `$02F6` and `$02F7` pending amplitude words of port 0 and port 1 (`0000` nothing pending, otherwise the amplitude to write plus one: `0001` means amplitude 0 and `0010` means amplitude 15); `$0340` and up the stack (one word is used and discarded per interrupt). Every variable is a 16-bit word. The BACKTAB cells are `$0200` to `$02EF`. A last-byte word holds the byte with the upper eight bits zero (for example `00C3`).

**A5 Initialization (frame 0), in this order.** (1) The graphics RAM card first: write `FF` to `$3800` to `$3807`. (2) Clear `$0200` to `$02FF` to `0000` (the BACKTAB and the variable area). (3) Store `00FF` at `$02F2` and at `$02F4`. (4) The PSG init writes (A7). (5) Store `03C5` at `$02F0`, the last store of initialization. (6) Enable interrupts and idle in a branch to itself. No interrupt service routine executes in frame 0: the first one executes in frame 1, so frame 0 is not displayed and the first displayed frame is frame 1. The idle loop is the only code that executes between interrupts; the program never halts and never executes `HLT`.

**A6 The interrupt service routine, in this order (every frame from frame 1 on).** (1) The display strobe: a write to `$0020` (the value is ignored); it is the first action. (2) A write to `$0021` (the value is ignored; it selects Foreground/Background mode). (3) Add 1 to the frame counter `$02F1`. (4) Deferred amplitudes: for port 0 then port 1, if its pending word is not `0000`, write pending minus 1 to its amplitude register (`$01FB` for port 0, `$01FC` for port 1) and set the pending word to `0000`. (5) Poll: for port 0 then port 1, read the port, keep the low byte, and compare it with the last-byte word; if it differs, store it as the new last byte, add 1 to the port's change counter (`$02F3` or `$02F5`), write the byte to the port's fine tone period register (`$01F0` for port 0, `$01F1` for port 1) and set the port's pending word to `0010` if the byte is not `FF` and to `0001` if it is `FF`. (6) Render: write the 16 lamp words of A3 for the two last-byte words, port 0 then port 1. (7) The gate: if at least one pending word is not `0000` (a port changed in this frame), write the channel C amplitude register `$01FD` with `000F` when the last byte of at least one port is not `FF`, and with `0000` when both last bytes are `FF`; otherwise do not write it. (8) Re-arm: discard the saved return address (the stack pointer goes back by one), wait a counted delay, enable interrupts and return to the idle loop. The program polls each port once per frame.

**A7 PSG rules.** The program writes a PSG register only in the ways listed here; every write is a CPU write of the stated 16-bit value. Init (frame 0, in this order): `$01F8` mixer `003C`, `$01F4` tone A coarse `0000`, `$01F5` tone B coarse `0000`, `$01FB` amplitude A `0000`, `$01FC` amplitude B `0000`, `$01FD` amplitude C `0000`. Afterwards a register is written only by the interrupt routine: the fine period of a port and the gate in a frame where a port byte changed (A6 steps 5 and 7), and the amplitude of a changed port in the next frame (A6 step 4). The log address of a write is the low nibble of the register address. Model facts the specification relies on (project profile rules PSG-R14, PSG-R15, PSG-R16, tier 4 or inference): mixer bits 0, 1, 2 disable tone A, B, C and bits 3, 4, 5 disable noise A, B, C (1 means disabled), bits 6 and 7 are the port direction bits (clear means input); a channel with both its tone and its noise disabled holds a constant level; the level of a channel whose amplitude register has bits 5 and 4 clear is the register's low four bits; a channel whose amplitude is 0 has level 0 whatever its tone does; the level of a tone-enabled channel with a non-zero amplitude alternates with the tone and its phase is not part of this specification. With the mixer `003C` tone A and tone B are enabled and tone C and all noise are disabled, so channel C is the program's constant-level gate. The tone period of a port is its fine register (the coarse register stays 0), that is the port byte; no tune, no scale and no envelope is used.

**A8 Timing statements a reader may rely on.** A frame lasts 59,736 ticks (14,934 CPU cycles of 4 ticks) and frame k spans the ticks 59,736 k to 59,736 k + 59,735. From frame 1 on, exactly one interrupt service routine executes in every frame; it starts within the first 40 cycles of the frame, its strobe is stamped before cycle 50, its port reads end before cycle 400, its deferred amplitude writes end before cycle 250, its fine period writes end before cycle 400, all 16 lamp words are written before cycle 1,200 and its gate write (if any) ends before cycle 1,300 (all counted from the frame start; the STIC register window of 2,000 cycles and the first BACKTAB row latch at cycle 3,848 both lie later). Consequently the port bytes read by the routine of frame k are the controller state in force at the start of frame k, an event at tick t is first read by the routine of the first frame k with t < 59,736 k, the delivered picture of frame k shows the lamps of the routine of frame k, and a frame is displayed exactly when its routine executed the strobe. Every event of the script lies more than 16,000 ticks from every frame start. The frame counter after the routine of frame k is k, so at a stop tick T that lies at least 10,000 ticks into frame floor(T / 59,736) the counter is floor(T / 59,736).

**A9 The scripted run.** Six controller events, each stating both words (`0x0` means no control closed), then four steps to absolute machine ticks, none of which stops at a halt:

| Event | at_tick | c0 | c1 |
|-------|---------|----|----|
| 1 | 100000 | KEY_1 | 0x0 |
| 2 | 220000 | KEY_1+KEY_9 | 0x0 |
| 3 | 340000 | 0x0 | DISC_E |
| 4 | 460000 | SIDE_TOP | DISC_E |
| 5 | 580000 | 0x0 | 0x0 |
| 6 | 700000 | KEY_1+KEY_9 | SIDE_LOWER_LEFT |

Steps: `run-to` 200000, 440000, 640000 and 806568 ticks. The run delivers the frames whose end tick is at or below the last stop. The PSG write log, the audio samples (one sample every 16 ticks, the 0-based sample i stamped (i + 1) x 16) and the frame slots are captured as `docs/runner.md` describes.

**A10 Not done.** No halt or quit input, no text, no glyph set, no graphics ROM read, no EXEC call, no data table, no moving object, no collision, no delay register, no border or color stack write, no noise, no envelope, no tune.

## (b) Runtime arithmetic (D-12, D-13, A-02, A-03)

The rules come first and the constants after them. A frame cycle is a CPU cycle counted from the frame start S_k (4 ticks per cycle, 14,934 per frame); "the routine of frame k" is the interrupt service routine that starts in frame k. Cycle counts are inference: they come from the cycle table of `data/cp1610/opcode-families.json` (cycles as printed; a branch 7 cycles not taken and 9 taken as policy C29; the SDBD pair 14 as policy C34), from the 9-cycle interrupt entry and the 12-cycle jump of the boot stub (`docs/cp1610/reference-notes.md`, an inference from the interrupt timing figure), and from the STIC figures of `docs/stic/timing-notes.md` (defaults C1 to C4 and C91 to C93). A figure that depends on the real console is not claimed.

### Rule R-S, the startup band (A-02)

The first `EIS` of the program starts at or after frame-0 cycle 3,777 and not later than frame-0 cycle 14,930. Then the level of frame 0 (it ends at cycle 3,791) cannot re-enter, the idle loop is waiting when the level of frame 1 starts, the first routine is the routine of frame 1 and starts at frame cycle 22 to 30, and frame 0 has no strobe: `frame 0 displayed == no`. The graphics RAM card is written first in the init so that it is complete long before the graphics-memory window of frame 0 closes (cycle 3,780).

Reference init, in the order of A5 (cycles from the first cartridge instruction):

| Block | Reference instructions | Cycles |
|-------|------------------------|--------|
| entry branch | `B` to the init code | 9 |
| card 0 | SDBD + MVII `$3800` to R4 (14), MVII `00FF` (8), MVII 8 (8), eight times MVO@ (9) + DECR (6) + BNZE (9, the last 7) | 14 + 8 + 8 + 190 = 220 |
| clear | MVII `0200` (8), CLRR (6), MVII 256 (8), 256 times MVO@ + DECR + BNZE (255 x 24 + 22 = 6,142) | 6,164 |
| last bytes | MVII `00FF` (8), two MVO (22) | 30 |
| PSG init | MVII `003C` (8), MVO (11), CLRR (6), five MVO (55) | 80 |

| jump to the `EIS` | `B` (9) | 9 |
| total up to the first `EIS` | | 6,531 |

The cartridge starts at frame-0 cycle E0 = 33 (the stub path alone: B 9, DIS 4, MVII 8, J 12) to at most 100 (the reset sequence before the stub is a profile figure, bounded here with a margin). Hence the card is complete by cycle E0 + 229 <= 329, which is at least 3,451 cycles inside the graphics-memory window, and the first `EIS` starts at frame-0 cycle 6,564 to 6,631: 2,787 cycles above the lower edge and 8,299 below the upper edge. The init ends with a jump to the `EIS` (it does not enter the delay of the re-arm: it already lasts longer than 3,776 cycles). Frame 0 has no bus windows (no strobe, so no latch): the cycle counts of the init are stall-free.

### Rule R-X, the strobe

The strobe is the first action of the routine, so it is stamped when the first routine instruction (MVO, 11 cycles) completes: at frame cycle t0 + 11 = 33 to 41. The register window closes at cycle 2,000, so the margin is at least 1,959 cycles; the mode-select write (the second routine instruction) completes by cycle 52. A strobe stamped at cycle 2,000 or later is dropped and the frame is blank (STIC-R22).

### Rule R-V, the render deadline

Every BACKTAB word of the 16 lamps is written before the first row latch (cycle 3,848), so the picture of frame k is a function of the controller state read by the routine of frame k alone (no row can latch a half-written lamp row). The reference sequence below finishes its last BACKTAB write at frame cycle 1,151 at the latest (table below): 2,697 cycles before the first latch (and 6,345 cycles before the latch of row 4, which is the first lamp row, at 7,496). The deadline of the specification is cycle 3,700: the work of the routine ends well before it.

### Rule R-E, the re-arm (A-03)

Let c_E be the frame cycle at which the `EIS` of the re-arm starts (counted with the bus-window stalls). In every frame 3,777 <= c_E <= 14,930.

- Lower edge. `EIS` is followed either by `PULR R7` (11 cycles, form A below) or by the branch of the idle loop (9 cycles, form B). EIS is not interruptible, so the first boundary that can accept is 15 (form A) or 13 (form B) cycles after c_E, and a unit starting at cycle 3,792 or later no longer sees the level: c_E >= 3,777 (form A, exact) or c_E >= 3,779 (form B, exact). The rule keeps the stated value 3,777 for both forms. Below it the routine re-enters in the same frame: two routines per frame, the counter doubles.
- Upper edge. The boundaries of the idle loop lie 9 cycles apart, so a routine starts at its usual t0 (22 to 30) only if the idle loop is already waiting when the level of the next frame starts at cycle 14,935; with `EIS` and one idle branch (13 cycles) this holds for c_E <= 14,930 (14,928 in form A). Above it the routine of the next frame starts later each frame (drift); once its strobe is later than cycle 2,000 the frame is blank, and once the `EIS` itself comes after cycle 3,778 of the next frame (c_E above 18,712) that frame has no routine at all.

The two forms, derived from the same two edges:

| Form | Re-arm | c_E | Band | Width |
|------|--------|-----|------|-------|
| A | pad loop of M iterations inside the routine, then `EIS` and `PULR R7` | t0 + (W - 18) + 8 + (15 M - 2) + stalls | 3,777 to 14,928 | 11,151 cycles |
| B | the routine ends `DECR R6`, `J wait`; `wait`: `MVII #N,R1`, N times (`DECR R1`, `BNZE`), `EIS`, then `B` to itself | t0 + W + 8 + (15 N - 2) + stalls | 3,777 to 14,930 | 11,153 cycles |

W is the work of the routine up to and including `DECR R6` and `J wait` (the budget below: 1,010 to 1,242 cycles). The widths differ by 2 cycles, so neither form is wider: the S-1 note's smaller margin for the in-routine pad came from tuning the pad close to the lower edge, not from the form. The default of A-03 stands: form B, because the routine releases its stack word before the delay and the delay count is the only number that sets the position of the `EIS`.

Numbers for form B (stall-free before cycle 3,791, then 108 to 117 cycles per bus window passed, 13 windows at most):

- Lower edge in iterations: the quietest routine (W = 1,010, t0 = 22) gives 22 + 1,010 + 6 + 15 N >= 3,777, so N >= 183 (c_E = 3,783; N = 182 gives 3,768).
- Upper edge in iterations: the busiest routine (W = 1,242, t0 = 30, 13 windows at 117 cycles) gives 30 + 1,242 + 6 + 15 N + 1,521 <= 14,930, so N <= 808 (N = 809 gives 14,934).
- The chosen delay is **N = 500**. Its c_E lies between 9,186 (quietest routine, t0 = 22, 6 windows at 108 cycles) and 9,597 (busiest routine, t0 = 30, 7 windows at 117 cycles): 5,409 cycles above the lower edge and 5,333 below the upper edge, about 355 iterations of room on each side.
- Mutant values (section (g)), chosen outside the band by more than the uncertainty of W and of the stall size: N = 100 puts c_E at 2,538 to 2,778 (999 cycles below the edge, re-entry in every frame); N = 1,150 puts c_E at 19,692 to 20,049, that is 4,758 to 5,115 cycles into the next frame, after the level has ended: that frame has no routine and only every second frame has one. The negative control N = 300 puts c_E at 5,862 to 6,129 (2,085 above the lower edge, 8,801 below the upper edge) and must still succeed.

### The counter rule (A-02)

The counter `[02F1]` counts routines; the routine of frame k brings it to k. At a stop tick T that lies at least 10,000 ticks into frame floor(T / 59,736) (the routine has finished: it ends by cycle 1,272, tick 5,088) `[02F1]` = floor(T / 59,736): T = 200,000 gives 3, 440,000 gives 7, 640,000 gives 10 and 806,568 gives 13 = `000D` (13 x 59,736 = 776,568 and 806,568 - 776,568 = 30,000). The older reading "floor(T / 59,736) + 1" belongs to the frame-0 band (an init that reaches its `EIS` before cycle 1,900) and does not apply here.

Settling rule. The rule of D-14 and the verification note (S4-2) is that no assert may depend on which of two consecutive frames shows an event. L2 holds because the gate of frame 10 (C to 0) precedes the deferred zero amplitudes of frame 11 (A and B to 0); between the gate of frame 10 and the amplitude writes of frame 11 the tone channels still sound, which is why no tick of that interval is asserted. Every asserted tick is a multiple of 16 (`audio at` requires the real sample period) and at least 10,000 ticks inside its window, and the same ticks and levels hold for `shift` and `swap` (the windows move by at most 200 ticks). The idle program has a single window, silence from tick 0 to the end (`audio at` 100,000, 400,000 and 800,000 all 0, 0, 0).

What is not asserted. The phase of a tone (the tick of an edge after an amplitude write) needs cycle-exact accounting and is never asserted; the levels of a tone-enabled channel with a non-zero amplitude are therefore not asserted either: channel A sounds from the amplitude write of frame 3 to that of frame 7 and from frame 9 to frame 11, channel B from frame 7 to frame 11, and both from frame 13 on, so every tick between L1 and L2 and every tick after the end of L3 is outside the asserted windows. `audio emitted` is not asserted: the stop of each step lies at the end of the instruction under way, which is not a hand-known tick, and 806,568 is not a multiple of the sample period of 16 ticks (50,410.5 samples), so the count has no exact hand-derived value; a stop that fell exactly on a multiple of 16 would deliver (tick / 16) samples (the 0-based sample i is stamped (i + 1) x 16).

### The carry reading of the lamp builder

Item (1) of section (j) was left open by the blind reader: the inputs it received did not state the shift rules. It is closed here without a change to the derivation. The builder is `COMR R1`, `SWAP R1`, then eight times `SLLC R1`, `MOVR R2, R3`, `ADCR R3`, `MVO@ R3, R4`: `SLLC` moves bit 15 into the carry and shifts left (`data/cp1610/vectors/shift.json`, `cpu.SLLC.n0`: `8001` gives carry 1 and `0002`, derived by hand from the shift table of the instruction manual, page 53), `ADCR` adds the carry to the register (`cpu.ADCR.carry-in-one`, `data/cp1610/vectors/register.json`), `MOVR` sets S and Z only and leaves the carry alone (the status column of `data/cp1610/opcode-families.json`: `MOVR` S, Z; `SLLC` with N = 0 S, Z, C; `ADCR` S, Z, C, OV), and the core meets all of these in the `cpu-vectors` suite, with the fault `ADCR_IGNORES_C` caught by the carry-in-one vector. The program is a second, independent statement of the same reading: the lamp patterns come out as the hand-derived frames F-S1 to F-S6 (hash asserts at frames 3, 5, 7, 9, 11 and 12 and the pixel probes of the four blocks all hold), which a carry taken from the wrong end or an `ADCR` that ignored the carry would have broken.
