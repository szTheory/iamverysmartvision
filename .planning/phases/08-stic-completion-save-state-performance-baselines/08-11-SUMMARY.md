A scratch Python decode of a snapshot (outside the tree) gave the same lengths, offsets, a contiguous section chain, the trailer SHA-256 and the schema digest. ## The two public calls

`ivs_machine_snapshot_size(m, out_bytes)`: out_bytes NULL BAD_ARG; handle BAD_HANDLE; out_bytes inside the instance BAD_ARG; OFF BAD_STATE; else the exact length. `ivs_machine_snapshot_save(m, buf, cap, out_written)`: out_written NULL, buf NULL with cap above 0, out_written inside the buffer BAD_ARG; handle BAD_HANDLE; out_written or the cap bytes at buf inside the instance, or a span past the top of the address space BAD_ARG; OFF BAD_STATE; cap below the length BUFFER_TOO_SMALL with the exact length in out_written. `state.save.refusal-ladder` holds 31 call rows (8 of size, 23 of save) and the success cases, each with the exact status, the exact out effect, the whole-instance memcmp and the buffer bytes unchanged, including the order rows (NULL handle with a NULL out, OFF with an overlapping out, OFF with a small capacity), buffers that end exactly where the instance begins and begin exactly where it ends (accepted), and one byte inside it (refused).

## The stepped literal

`stepped-snapshot-sha256` is `087a15d3fce834b1d944bbbd74385d029e42eb4a4f9f0fbb322d754df0755b6b`, the SHA-256 of the whole snapshot of the stand-in boot program stepped **5,000 units** after the power-on reset. The program is the four PSG writes of the stand-in tone program followed by the RAM loop of the first stand-in program, 23 decles all taken from `tests/machine/machine_standin.c` (the back branch is relative, so its displacement 4 is unchanged). Chosen by arithmetic: the setup is 9 units and a loop pass is 3 units of 26 cycles (MVO 11, INCR 6, taken branch 9), 104 ticks; the first tone edge needs 65,536 ticks and a frame is 59,736, so 5,000 units (about 1,664 passes) reach past the first edge and the first two frame ends and stop in the middle of the third. The test asserts the facts instead of trusting the arithmetic; measured once when the literal was pinned: 43,338 CPU cycles, 173,352 master ticks, `stic.frame_index` 2, `obs.video.count` 2, `obs.audio.count` 6,739 level changes, `obs.audio.emitted` 10,834, `obs.psglog.count` 4, `[$0200]` and R1 `$07D4`, `[$01F8]` `$003E`. The literal is a self-recorded repeatability pin (labelled so in the data file), never evidence that the state is right; the same literal passes in the dev and release presets, which is the proof of identical snapshot bytes across the two builds (it also passes in the Ubuntu container, gcc 13).

## Deviations from Plan

## Decisions Made

- The parameter digest binds the numbers of the profile tables and the profile id (the id travels in its own header field), never any text of a cite: a provenance edit must not invalidate a snapshot, a value edit must.
- Everything that can refuse is decided into locals before the first byte of the caller's buffer is written; the buffer is then written once, sections first (so lengths are known), header and table after, the trailer last.
- The oracle files were only appended to (`ivsn-literals.ids` two blocks, `ivsn-v1.md` one section, `tests-pending.ids` one deleted line by lesson 3); the Classes section SHA-256 is still `e23d78160147e71915eca6c0b34da888ad34fe432652de18f36003a09b3eb179`, `data/state/schema.literal.txt` and `data/expected/state-checklist.ids` are untouched.
