## Goal achievement

The goal is met in the sense the gate can test. A guest writes the STIC registers, graphics RAM and BACKTAB through the bus; accesses inside the profile windows take effect and accesses outside them follow the blocked-access policy (reads return the undriven fill, writes are dropped and counted); the VBLANK interrupt level and the 13 bus-request windows occur at schedule times derived from the profile fields (event ticks 8,000, 15,120, 15,164, 15,392 + 3,648 i inside a frame of 59,736 ticks) and cost the CPU exactly `w + 468` ticks per window, with unit time tiling elapsed time and the same instance bytes under any slicing; each frame is delivered at the frame event into a caller-owned buffer as a 15,296-byte slot (32-byte header and 159 x 96 index bytes) with a per-frame digest chain that the runner re-hashes from the slots it received; Foreground/Background and Color Stack cards render the ten hand-derived frames of plan 06-01 exactly, in process, through the runner and through the installed package; and `ivs_machine_peek` and `ivs_machine_stic_state` inspect the STIC without any side effect (a peek of the mode-select address never switches the mode). The original diagnostic `ivs-diag-stic-1` reaches the hand-derived frames from a power-on reset in both modes.

What the goal does not include, and the record does not claim: that the register map, the strobe and alias behaviour, the access windows (2,000 and 3,780 CPU cycles), the interrupt width (3,791), the bus-window table, the hold (114), the card word layout or the Color Stack rules match a console. Those rest on tier 4 community sources, inference or labelled defaults, and are the handed-off items below. It also does not include MOBs, border, delay and collision (VID-05, Phase 8) or a sustained picture (the boot stub has no interrupt routine, so a guest shows one frame; a project interrupt routine is a Phase 7 need).

### Independent recomputation (verifier, scratch directory under `mktemp -d` outside the repository, nothing committed)

Two short scripts (python 3 with `-I`) read only the committed profile (`data/profiles/intv-2609-ntsc-family-p1.json`), the frame literals and the delivered runner output; no value was taken from a SUMMARY. The executor's earlier recomputation (same quantities, plus the chain framing) is not repeated here and the chain framing digests h0, h1, h2 and `digest.video` were not recomputed by the verifier (they are re-hashed by the gate: `video.chain.framing-oracle`, `runner.vchain.*`, `video.chain.check pass` on both scenarios).

- Event ticks from the profile fields `ticks_per_cpu_cycle` 4, `cpu_cycles_per_scanline` 57, `scanlines_per_frame` 262 and the `stic.*` cycle fields: frame 59,736; register window 2,000 x 4 = 8,000; graphics-memory window 3,780 x 4 = 15,120; first bus window 3,791 x 4 = 15,164; first row fetch 15,164 + 57 x 4 = 15,392; pitch 912 x 4 = 3,648. All equal the values the record and `docs/stic/timing-notes.md` state.
- Resume time of a window: `4 x (114 + 1 + 2) = 468` ticks (hold 114, `bus.release_latency_cpu_cycles` 2), equal to the closed form `w + 468`.
- Window count: windows that start inside a frame of 14,934 cycles: 13, equal to `stic.bus.count`; a 14th would start at cycle 15,647, past the frame.
- Slot and capacity: slot `32 + 159 x 96 = 15,296` bytes; `D / F = 4,194,304 / 59,736 = 70`; `70 + 1 + 1 (stic.video_slack_frames) = 72` slots; `72 x 15,296 = 1,101,312` bytes; `D` is the `--slice-ticks` maximum of `docs/runner.md` (1 << 22).

## 3. Accepted caveats

- **Shared misreading.** One author wrote the register literal, the card literal, the frame literals, the derivations, the listing and the core; one model family read the pages. The blind second reads (`docs/stic/second-read-record-*.md`, 2026-11-12, all four families recorded, none pending) are the same model family reading the same pages: registers 64 of 64 rows agree on role and class (the 128 mask cells were answered unknown by design), card bit roles 62 of 64 agree (2 convention differences on the select bit of the Color Stack GROM and GRAM words, same semantics), frames 10 of 10 identical (the headers carried the decoded fields), geometry 14 of 20 keys agree on value after spelling normalisation, 6 answered unknown and 0 disagree on a sourced value. A transcription cross-check, not independent evidence. Agreement between the pieces is not evidence about a console. This record's author is the same model family as well: it re-ran the code and re-derived the arithmetic, but it read no console, schematic or data sheet.
- **Tier 4 register and card literals (one lineage).** The register map, the strobe and alias behaviour, the Color Stack rules and the card word layout come from the wiki STIC page (revision 15008), the memory map page and the BACKTAB page, which are likely one lineage (C81, C84, C96 to C98); only the geometry counts, the 14-bit bus, the 12 rows and the 240-word BACKTAB are tier 1.
- **Page-reading verdict of plan 06-01.** The 1980 and 1982 catalog pages print structure and electrical data for the STIC but no register address, no read behaviour and no timing of the access windows; every window, hold and interrupt figure is therefore tier 4, inference or a labelled default, and the claims that rest on them stay provisional.
- **Policy numbers are proven by perturbation and accounting identities, never as expected values.** The windows (2,000 and 3,780 cycles), the hold (114), the interrupt width (3,791), the release latency (2), the power-on state and the frame phase are profile fields; the tests move each field and require the model to follow, and the accounting identities (units tile elapsed time, resume at `w + 468`, 13 windows against the printed bound of 13 or 14) hold for any value. No test asserts that the default is the console's value.
- **`.digests` goldens are repeatability only.** The two scenario goldens and the consumer golden are self-recorded by the emulator: they show that the same machine produces the same bytes under the runner and the installed package, not that the bytes are right. The `.expect` files are hand-derived (tier `original-diagnostic`), written from the derivation before the scenarios existed, with the order caveat of the 06-13 summary (the three scenarios were run once before the `.expect` commit; no assert line changed afterwards).
- **Frame granularity.** BACKTAB is latched per bus window into 12 row latches (row-granular fetch) and the picture is rendered at the frame end (frame-granular render); a write during active display tears at row granularity (C100). Mid-frame register changes and the border are not modelled (Phase 8).
- **159 versus 160 columns (D8).** The published width follows the only tier 1 count; the reversal is the one profile field `video.last_card_column_px` (8 gives 160) and a re-bless of the goldens as one classified diff, or a new format id (C10 stays `partial`, C101, C105).
- **C41 re-entry consequence and the DIS-first interrupt routines.** With `cpu.interrupt_accept_clears_intff` 0 a service routine that does not start with DIS is entered again at every open boundary while the level is held (about 250 entries per frame); the in-process stand-in routines are DIS-first and the vector family covers both field values. The diagnostic has no interrupt routine, so the DIS-first rule is not exercised in a guest; a project interrupt routine is a Phase 7 need.
- **06-13 findings.** The listing checker decodes data tables as code (a data directive is a Phase 7 need); the derivation's cycle budget ran 31 cycles above the observed run without the strobe (an inference gap, no budget figure is asserted anywhere); the `BITS` column came from a scratch formatter so the `listing-bits-mismatch` check was not exercised by it; the D4 crossing rule was not crossed (133 words, 5 branches, 0 checker escapes), and the decision for a fourth diagnostic moves to Phase 7.
- **The default alias sensitivity is the only value run end to end.** `stic.alias_read_sensitive` 0 is range-checked in the machine suite but no test runs the machine with it (recorded in C84).
- **The planner's resolver choices keep the D10 inventory at 42.** Open discrepancies whose resolver starts `test:` (C38, C41, C52, C84, C90, C91, C93, C94, C102 to C104) and `pending:` (21 of them) do not add owner items; only `measurement:` resolvers are listed, and every one of them has a line (the step fails otherwise).
- **Budget note with the normalised ratio.** Hosted rows since the Phase 5 close read 75 to 131 s and 210 to 433 cpu-s; the last five give a gate median 101 s, cpu median 315 and `r = cpu_s / build_s` median 7.64 against the budget 7.8 and the revisit line 8.3; one run (131 s) exceeded the 130 s any-run bound and is judged runner noise (single sample, the next row is 87 s). `phase6-close: no-lever` (`.planning/CI-EFFICIENCY.md`). The container gate and the dash gate take minutes on a loaded laptop; the hosted rows after this push are the arbiter.
