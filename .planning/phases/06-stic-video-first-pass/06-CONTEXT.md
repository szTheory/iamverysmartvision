<domain>
## Phase Boundary

The STIC becomes a real device: control path, access windows and the display-enable handshake, a deterministic frame timeline with the VBLANK interrupt and BUSRQ/BUSAK bus stealing at profile-defined machine times, and a raw palette-index framebuffer produced at a defined machine-time boundary for background cards in Foreground/Background and Color Stack modes, checked against hand-derived frames with no GROM image.

In scope: VID-01, VID-02, VID-03, VID-04, VID-06, and decisions D8 (framebuffer geometry) and the D3 STIC part pin.
- STIC register file at `$0000-$003F` with masks, access windows, blocked-access policy, display-enable handshake, color-stack mode switch, a side-effect-free inspection path.
- Frame timeline (262 lines x 57 cycles), INTRM VBLANK level, 13 bus-steal windows, the catch-up discipline, the effect on published bounds.
- Raw framebuffer buffer, geometry, format, digest domain 16, frame stop, ABI/runner growth, `ivsr 3`.
- Card rendering, hand-derived literal frames, a third original diagnostic fixture, installed-consumer replay.

Not in scope: MOBs, collision registers, vertical/horizontal delay, border extension, mid-frame register effects (Phase 8, VID-05), a project interrupt service routine in the boot stub (Phase 7), host display or palette, PAL, ECS, a macOS CI leg, claims about real hardware (D10), runs with the owner's EXEC/GROM (D11).

## Implementation Decisions

### Evidence posture (all requirements)

- **D-01:** The page-reading verdict comes FIRST (oracle plan 06-01, no C): the GI 1980 printed 5-10..5-12 (pdf 191-193) and 1982 printed 9-43..9-45 STIC pages, and the RA-3-9600 page (1980 printed 5-18, pdf 199; 1982 9-51), are read as images and judged honestly. Pre-reading by two research agents found a pin, bus and electrical data sheet: they print structure (14-bit bus, 20x12 matrix, 7-pixel 20th column, 159x96 visible of a 167x105 grid, 240 14-bit words, SR1/SR2/SR3 sync, bus copy mode entered on INTAK and left at the first BUSAK edge, a 1.79545 MHz clock that supports C8) but NO register address, bit field, color stack, delay or window length. Therefore every register-level, card-bit and window fact is tier 4 (one community lineage) or `unknown-default-chosen`, every claim built on them is `provisional`, and the plan must record the verdict (and whether the unread timing figure on 5-12/9-45 prints usable numbers) before any implementation. If the pages do print more, the affected rules move up a tier; the plan structure does not change.
- **D-02:** Oracle-first, as Phase 5: expected values are authored from sources and hand derivation before the code (register literal, geometry literal, card tables, about 8 literal hand-derived frames as text with a per-card pixel-count conservation check and a hash tie to the `.expect`, blind second derivation by isolated readers using blinded copies under `build/review/`). No second renderer, no emulator or generated expected values. Policy numbers (windows, hold lengths, interrupt width, power-on state) are never expected values: they are proven by profile perturbation, accounting identities and the printed 13-or-14 bound.
- **D-03:** D3 STIC pin: AY-3-8900-1 NTSC (confirmed on the pages); PAL AY-3-8900 out of scope. `stic.part` is a tier-tagged field.

### STIC device and access model (VID-01, VID-06)

- **D-04:** The STIC register file is a real memory-system device (new device kind `stic14`, per-register write/read masks from a generated `stic.regmap`, the PSG precedent: region flip from stub to real in the device plan, memmap literal split by width, `ivs_stic_state` struct, `IvsStic*Table.cmake` generator, fail-closed). All side effects (the `$0021` mode switch, the handshake strobe) live in the machine bus wrapper, never in the memory system's read, so `ivs_machine_peek` stays pure and inspecting `$0021` cannot switch mode by construction. One new public const call `ivs_machine_stic_state()` returns the stored registers, mode, color-stack pointer, display latch and frame state that the CPU bus view cannot show (VID-06); it has no side effects and joins the api-effects registry.
- **D-05:** Access windows are a pure function of the access stamp (timing note T-6, which wins over the register note's copy-mode event machine for the mechanism): STIC registers accessible iff `0 <= stamp - S_k < 4 x stic.reg_window_cpu_cycles` (default 2,000; alternate 2,900), GROM/GRAM iff `< 4 x stic.gmem_window_cpu_cycles` (default 3,780; alternate 3,796); C1/C2 stay `unknown-default-chosen`. The windows apply whether or not the display latch is set (`stic.access_gating_when_off = apply`, `unknown-default-chosen`, new discrepancy, risk and reversal recorded). The memory system's existing gates (`IVS_MEMSYS_GATE_STIC_REGS`, `IVS_MEMSYS_GATE_GMEM`, in the digest as `mem.gate_open`) are flipped by the STIC event handlers at catch-up. The register note's INTAK/BUSAK bus-copy-mode mechanism is recorded as the alternative hypothesis with its page citation (reversal: owner hardware measurement D10, or a primary page that prints window events).
- **D-06:** Blocked policy (C5, unchanged default): a blocked write is dropped; a blocked read returns `memmap.undriven_read` (`$FFFF`); both are counted in state for the inspection path. Display-enable handshake (C6 default): a write to `$0020` inside the register window sets the display latch for the current frame; the latch is cleared at every frame start, so the guest must strobe it each frame; a clear latch at the first window gives a blank frame (no windows, no row fetch, the frame is still produced and counted). Color-stack mode is persistent: a read of `$0021` (and its alias reads) switches to Color Stack, a write selects Foreground/Background; the color-stack pointer resets to 0 each frame (cards note R). Register widths, masks, read-back values and the alias set are tier 4 / default per the register note's rule table (28 rules with basis labels) and its profile schema; the planner takes names, masks and field keys from `06-DISCUSS-regs.md` section 5/6.

### Timeline, VBLANK and bus steal (VID-02)

- **D-07:** Frame timeline (timing T-1): `F = ticks_per_cpu_cycle x cpu_cycles_per_scanline x scanlines_per_frame = 59,736` master ticks, constant; frame k covers `[S_k, E_k)` with `S_k = stic.frame_phase_ticks + k x F` (`frame_phase_ticks = 0`, `unknown-default-chosen`, new discrepancy) and `E_k = S_{k+1}`. The frame index and an event cursor are device state (`ivs_stic_state`), never derived from the tick by modulo. `docs/time-base.md` is corrected (the Frame glossary and the "never derived by modulo" sentence) BEFORE any STIC code.
- **D-08:** VBLANK interrupt (T-2): INTRM is a level asserted for `4 x stic.irq_low_cpu_cycles` ticks from each `S_k` (`irq_low = 3,791` cycles, C3 wiki figure, `unknown-default-chosen`; alternates 2,907/2,920 recorded), independent of the display latch. The CPU stepper is unchanged: Phase 6 only drives `lines.intrm` and `lines.busrq` (hard-wired to 0 today). Line sampling lag `bus.line_sample_lag_cpu_cycles = 1` becomes a profile field. C41 (acceptance does not clear INTFF) stays 0; consequence stated in the plan: an ISR that does not start with DIS is re-entered at every open boundary while the level is held, so every Phase 6 original diagnostic ISR is DIS-first and a vector family covers both C41 values.
- **D-09:** Bus steal (T-3): `stic.bus.count = 13` windows per frame (only if the display latch is set when window 0 would start), window i starts at `first_start + i x pitch` cycles from `S_k` (`first_start = 3,791`, `pitch = 912`), BUSRQ held `H = 114` cycles (C4 wiki figure, `unknown-default-chosen`; alternates 110 and 57/44 recorded); window 12 steals time and fetches nothing in Phase 6. The stall is the stepper's existing `BUS_GRANT` unit sequence (1-cycle grant, hold units, 2-cycle release `bus.release_latency_cpu_cycles`, a closed boundary defers the grant). Display off: no windows, the CPU keeps 14,934 cycles per frame; display on about 13,518 (the printed bound is 13-or-14 windows; planned totals sit within 0.9% of the community aggregates, tier 4). Every constant is a tier-tagged profile field with its discrepancy id (C1-C4 stay `unknown-default-chosen`; new C81.. per the allocation table).
- **D-10:** Catch-up discipline (T-5, A-02 of Phase 5 applies): the STIC is advanced to the access stamp before any STIC access and to the unit boundary at the end of EVERY unit in the run and the step seam alike (the PSG rule), so nothing depends on how the host slices run calls. Bounds are re-proved, not assumed: `U = 468` and `g = 28` stay (the probes are re-run through the full machine, including bus-grant units); the Phase 4/5 audio and log capacity numbers and goldens stay bit-identical; the plan states exactly what a bus-grant stall changes in the per-unit bounds and proves it with a probe.
- **D-11:** Rendering granularity (timing T-7, wins over the card note's pure frame-granular render): row-granular FETCH, frame-granular RENDER at `E_k`. BACKTAB is latched per bus window into 12 row latches (13 x 20 words state in `ivs_stic_state`, about 520 bytes); registers and GRAM/GROM are frozen over graphic time by the access windows (D-05) so the render at `E_k` from (registers at `E_k`, GRAM/GROM at `E_k`, the 12 row latches) equals a scanline-accurate draw under the window model; a mid-frame BACKTAB write tears at row granularity. The card-to-pixel function is pure (`registers, glyph source, row latch -> index plane`); static fixtures are identical under any granularity. The freeze rests on C1/C2 estimates (reversal recorded: if windows leak, grow the latch to registers and GRAM, composite re-bless, no API change). Phase 8 (MOBs, delay) needs only the window table and the render function.

### Frame, buffer and API (VID-03)

- **D-12 (D8, decided):** Published geometry: 159 columns by 96 rows of display rows (each display row is 2 TV lines, published as metadata); width = `19 x 8 + video.last_card_column_px` where the profile field `video.last_card_column_px` is 7 (tier-1 count from the GI pages, 1980 p.5-10 and 1982 p.9-43: 159 visible of 167; the clip side and bit order of the 7-pixel column are tier 4); a profile with 8 gives 160 and reverses C10 (`partial`, one-field reversal). The renderer produces 20 cards wide and crops to the published width. The 167x105 nominal grid, border and blanking are not published as pixels in Phase 6 (a border/blank position inside the window is index per D-13).
- **D-13:** Pixel format: one byte per position, the 4-bit STIC color number 0..15 (the card note's color-number plane, no palette, RGB or presentation in the core); `0xFF` = position not displayed (the not-drawn/cut-off sentinel); display-off frames fill with the border color index (`unknown-default-chosen`). Slot = 32-byte big-endian header (`tick` = `E_k`, `index`, `width`, `height`, `flags`) plus the plane (15,264 bytes + header = 15,296 per slot with 159x96); format id `IVS_OUTPUT_FORMAT_INDEX8_FRAMES_V1` appended to the output-format list (0 stays NONE). Rows are tightly packed, row stride = width.
- **D-14:** Frame boundary and frame stop (timing T-8, frame F-6): a frame COMPLETES at the first unit boundary `>= E_k`; its content is fixed by events `<= E_k` (step-first-then-write, as the PSG). The reserved run flag becomes `IVS_RUN_F_STOP_ON_FRAME = 2` (the Phase 4 test that refused it is inverted, a reviewed change): effective target `T' = min(target_ticks, E_next)`, the run behaves as `run(T')`, new append-only stop reason `IVS_STOP_FRAME = 5`; exit-state order INTERNAL, GUEST_FAULT, CPU_HALTED (flag), FRAME, TARGET; overshoot stays against the caller's target. Report v3 appends `video_first_index`, `last_frame_end_ticks`, `next_frame_end_ticks` (the exact offsets and sizes follow from the final field list, pinned by the plan with 64-bit pointer math); `ivs_info` v4 appends `frame_phase_ticks`, the video geometry (`video_width`, `video_height`, `video_slot_bytes`, header bytes) and the frame-spacing fields; `video_frames_completed` and `video_bytes_written` become live. At most one frame completes per flagged call; a flagged call needs one slot.
- **D-15:** Video capacity (timing T-9, frame F-7): the Phase 4 `+1` formula is violated in a corner (61 of 400,000 runs); video uses `required = video_slot_bytes x (D/F + 2)` with a new env member `video_slack_frames = 1`, NULL with capacity 0 meaning not requested (Phase 5 D-17), refusal before any state change, a pre-unit guard to `IVS_STOP_INTERNAL` that is never expected, named fault `VIDEO_CAP_PLUS_ONE` that must fail the corner test. Audio and log capacities and goldens do not change.
- **D-16:** Digest (timing T-10, frame F-9): domain 16 (VIDEO, observation, outside the composite) becomes a per-frame chain `h0 = SHA-256("IVS-VIDEO-LOG-V1")`, `h(n+1) = SHA-256(h(n) || slot bytes)` over exactly the delivered slot bytes (header plus plane) streamed through the incremental SHA-256, so the runner re-hashes it from delivered bytes (`video.chain.check`, as the audio chain); the chain is per frame not per call, so slicing invariance holds by construction (the Phase 4 `index || len || record` framing is NOT reused). STIC registers join MEM (domain 2) and `ivs_stic_state` joins INSTANCE (domain 4); the composite goes 2 -> 3 (Phase 5 pattern: pin the v2 literals first, bump, re-bless with a classified diff: only composite, instance, mem and video lines may move; machine time, units, cycles, stop reasons, audio and psglog chains must not). Phase 4 and 5 fixtures use no EIS and never strobe the display, so their unit sequence is identical: "phase 6 does not move any phase 5 timing" is a named acceptance test.
- **D-17:** Runner (frame F-12..F-15, verify V6-14): `ivsr 3` (one bump), `capture video`, `assert frame <n> pixel <x> <y> == <idx>` and frame hash / chain asserts, `video.chain.check`, new keys after the audio keys, operator-only `--video-raw <file>` (exclusive create, the Phase 5 cleanup-on-failure rules) and an operator-side PPM/PNG export helper outside the core and outside the evidence path (an optional human-viewable artifact, no tool-based judgement of look). IVSS parser reasons append. No SHA code in the installed consumer beyond what the Phase 5 consumer replay already compares through the golden.

### Card rendering (VID-04)

- **D-18:** Pure renderer producing the 20-card-wide index plane then cropped (D-12): BACKTAB word formats for Foreground/Background and Color Stack, the 16 colors, GROM/GRAM select, 8x8 card rows, bit order, the 7-pixel 20th column, Color Stack advance before draw with reset to 0 each frame (cut-off column counts), Colored Squares implemented with a documented cut line (`06-DISCUSS-cards.md` R-1..R-18 and rule table CR-01..CR-17 are the spec; field layouts are tier 4 and the register-side semantics belong to D-06). Layout is hard-coded (the card note), not profile data, but every uncertain bit role is a named discrepancy with a profile-visible default and the fault list of the card note (wrong mode bit, stack not advancing, bit order reversed, GROM/GRAM swapped, 20th column width) is the named-fault set.
- **D-19:** No GROM in CI or in any fixture: glyph data comes from project-authored original GRAM card bitmaps written by tests through the existing raw-poke seam (`ivs_memsys_poke_raw_internal`) and by one end-to-end guest fixture through the bus. The renderer reads memsys backing through dedicated accessors, never the CPU view or gates, so rendering has no read side effects. Expected frames are literal text files (about 8, 20x12 cards x 8 rows, kept as reviewable text) under a fixture grammar from the card note, with a test-only word-vs-fields encoder and a 64-probe bit-role sweep as the independent encoder check.

## Amendments from research (override the matching text above)

Research (`06-RESEARCH.md`, executed against the code) found these CONTEXT assumptions false or incomplete. These amendments are binding and win over D-01..D-24 where they differ.

- **A-01 (D-04):** the read alias `$0040-$007F` cannot stay a stub: `IvsMemmapTable.cmake` forbids a half-stub, half-real STIC, so ALL five STIC regions flip to real together in the device plan (the literal, the memmap suite rows and the width probe move with them).
- **A-02 (D-14):** `IVS_RUN_F_RESERVED_FRAME` is the vehicle of one dedicated refusal test and five generic call sites in three test files plus `api-effects.json`; the flip to `IVS_RUN_F_STOP_ON_FRAME` replaces those with another unknown bit in the SAME commit.
- **A-03 (D-17):** the runner is not isolated to the runner plan: `ex_plan_buffers` and the always-set STOP_ON_HALT break every scenario the moment video capacity (`+2` slack) is real, so the runner/consumer buffer request lands in the same plan that makes the video layout real (the Phase 5 audio precedent), not later.
- **A-04 (D-20):** the diagnostic is NOT cycle-count free: under D-05/D-06 the display strobe must land within the 2,000-cycle register window after tick 0 (frame 0 windows: registers 8,000 ticks, GRAM 15,120 ticks) and the guest must not HLT before the first frame end; the `.expect` derivation is against the frame-0 windows and precedes any listing, and the SDBD checker rule lands first.
- **A-05 (D-11):** the row-latch state is 12 rows x 20 words = 480 bytes (not 13 x 20); window 12 fetches nothing. Instance size growth is derived by the plan's own layout math (research: 113,760 to about 114,416).
- **A-06 (D-14):** the tie rule is the PSG one (step first, then write): a write stamped exactly `E_k` lands in the NEXT frame; frame k's content is fixed by events stamped strictly before `E_k`. "Events `<= E_k`" in D-14/D-16 reads that way for the timeline events (FRAME_END(k) before FRAME_START(k+1)), not for guest writes.
- **A-07 (D-04, D-06):** alias reads of `$4021`, `$8021`, `$C021` decode to the cartridge in the read view, so the mode-switch hook keys on the access address before decode (the write view/stamped access), not on the memory-system read.
- **A-08 (D-15):** the "61 of 400,000" violation count came from the note's scratch script and was not reproduced; the corner itself is real and is constructed (now = `E_k - 4`, D = `F - 1`, a unit crossing the target completes a second frame). Tests use the constructed corner.
- **A-09 (D-10):** verified by executing the real stepper with driven lines: a bus window starting at tick `w` resumes the CPU at `w + 468` (the unit is 117 cycles of grant, hold and release); windows are granted only at open boundaries (a stream of MVO is never stalled or interrupted); with C41 = 0 a NOP loop with INTFF held takes 253 interrupt entries per frame; the densest PSG writer does 1,659 writes per frame with the display on or off, below `W_log = 2152`. The bounds re-proof therefore confirms U = 468 and g = 28 and must still be re-run through the full machine with driven BUSRQ in the plan.
- **A-10 (D-12, D-17):** candidate sizes from the research: report v3 = 160 bytes (fields at 136/144/152), `ivs_info` v4 about 320 (312 minimal, starting at offset 288), request stays 80; the plan pins the final numbers.
- **A-11 (D-23):** plan shape: the research recommends re-cutting to up to 14 plan slots (06-03 ABI/profile growth and 06-04 register file/composite split in two, and the new public const call `ivs_machine_stic_state` in its own small plan). The planner may re-cut to 12-14 sequential plans within the caps (5 tasks, 8 faults, 25 controls) and must keep the hard sequencing (oracle plan first with the one allocation table of discrepancy/claim/D10 ids across the five notes; ABI before any grown field; device before timeline before framebuffer before cards; runner and consumer before the diagnostic). ## Reconciliation (conflicts between the five notes)

- **Window mechanism:** the register note derives the windows from an event machine (bus copy mode entered at INTAK, left at the first BUSAK, plus a V-anchored register window); the timing note uses a pure function of frame position with the community figures. Decided: the pure schedule (D-05); the copy-mode idea is the recorded alternative.
- **Rendering granularity:** the card note chose a pure frame-granular render from live state with no added state; the timing note chose row-granular fetch (12 BACKTAB row latches) with a frame-end render. Decided: the timing note (D-11); the card-to-pixel function is the same, so static fixtures are unaffected.
- **Frame width:** the frame note publishes 159 columns; the card note keeps a 160-wide plane with column 159 = `0xFF` and an optional "set" plane. Decided: published width from the profile field (159 now), `0xFF` as the not-displayed sentinel, no "set" plane (D-12, D-13).
- **Frame boundary:** the frame note says end of the display period (SR1), the timing note says `E_k = S_{k+1}`; these are the same instant (the raster event that starts VBLANK). Decided: `E_k` (D-14).
- **Frame stop:** the verification note recommended keeping the reserved flag unused; the timing and frame notes both specify `IVS_RUN_F_STOP_ON_FRAME`. Decided: implement it (D-14): VID-03's "defined machine-time boundary" is cleanest as a frame event, and the cost is one append-only reason and a reviewed inverted test.
- **Flag name and sizes:** `IVS_RUN_F_FRAME_STOP` (frame note) vs `IVS_RUN_F_STOP_ON_FRAME` (timing note): the latter (consistent with STOP_ON_HALT). Report/info sizes differ between notes (152/312 vs 160/v4): the final sizes follow from the union of fields in D-14 and are pinned by the plan's own pointer-width math.
- **Digest chain framing:** the frame note proposes a chain over slots plus a separate plane hash for asserts; the timing note a chain over frame index, `E_k` and bytes. Decided: a chain over the exact delivered slot bytes (D-16, the header carries index and tick); the plane hash for pixel-hash asserts is a runner-side value, not a core domain.
- **Frame digest vs capacity slack:** both agree on `+2` (D-15).
