## Sampling Rate

Nyquist reasoning: the quantity that can change between two feedback samples is "one task's diff"; every task therefore has an automated sample that fails for the intended reason, and no three consecutive tasks go without one. The two derived-constant probes of the research (the CPU stepper under a driven schedule, the struct arithmetic) are re-created as in-repo tests so the sample is not a one-off.

- **After every task commit:** the quick command for the touched family (`--only <prefix>`, under 5 s), or the touched pure step through `sh tools/gate.sh` when a step or inventory changed, or `sh tools/check/run-controls.sh` (`controls=N/N` last line) when controls changed.
- **After every plan (waves are sequential; a plan is its own wave):** `sh tools/gate.sh` and `dash tools/gate.sh`, both ending `gate: PASS` with the plan's exact `steps`, `controls`, `faults`, `tests-expected` counts, and a recorded plain-run time per preset for any new suite (SUMMARY habit from Phases 4 and 5).
- **Before pushing every plan marked `linux` below:** `sh tools/gate-linux.sh` green (hosted-only classes: gcc argument evaluation order, `-Wconversion`, `-Wmaybe-uninitialized`, `-Wformat-truncation`, PIE and `_GLOBAL_OFFSET_TABLE_`, GNU `nm` shapes, glibc names, cmake 3.28 policy).
- **Golden-touching plans (06-04a, 06-04b, 06-06 only if a scenario passes the first frame end, 06-09, 06-10):** the last task regenerates the affected goldens with `ivs-run --update-golden` and records the CLASSIFIED diff in the SUMMARY (rule per plan in `06-RESEARCH.md` Pitfall 1: 06-04a moves only `digest.mem`, `digest.instance`, `digest.composite` of the four `.digests`; with the complete event table in 06-04b no later plan moves an existing `.digests`; `digest.cpu`, `digest.images`, `digest.audio`, `digest.input`, `digest.psglog`, every `step.*`, `slot.*`, `cpu.*` line byte-identical); `pkg-consumer.golden` follows (its `video_format` line moves in 06-06); never hand-edited.
- **Oracle-first ordering:** every implementation SUMMARY names the oracle commit (06-01) that precedes the implementation commit; the verifier checks `git log` order. Within 06-04a the v2 literal pin is the first commit.
- **Before `/gsd-verify-work`:** gate green under sh, dash and gate-linux with the final counts; hosted `gate_s` and `cpu_s` rows recorded by the orchestrator; D-45 rule and the normalised metric evaluated; VERIFICATION three tables (automated, handed off, accepted caveats).
- **Cost discipline:** judge self-controls and controls before faults; one in-process loop per matrix; fuzz schedules at most 100,000 ticks per seed (about 1.7 frames); video tests run few frames (one default slice of 71 slots is about 9 ms of SHA-256); runner-process slice 1 and slice 7 variants only for `diag-stic-fgbg-pass`; scenarios capped at 150,000 ticks; no `sleep` or wall-clock in any new test; any new waiting shell construct uses a polled marker with a bound, never a blocking FIFO.
- **Max feedback latency:** 75 s hosted median `gate_s` (budget), local quick samples under 5 s.
