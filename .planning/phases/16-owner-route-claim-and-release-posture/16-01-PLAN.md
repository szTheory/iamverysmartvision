    `cmake --build` invocation it makes in one `mkdir` lock at `<results-dir>/.build-lock`, releasing it on
    both the success and the failure path and on HUP/INT/TERM. The lock is needed and its reason is a
    measurement, not a worry: two concurrent `cmake --build --preset dev` runs on one tree were measured this
    session to fail at link time (`clang: error: no such file or directory: 'core/libivs_core.a'` — one run
    archiving while the other links), so "both builds are no-ops because `c-build` already built everything"
    is a precondition, not a guarantee, and a lock makes the overlap safe without depending on it. The wait
    is bounded and polled in the house style (`sleep 0.01`, a poll cap of about 60,000 iterations, i.e. ten
    minutes), and on expiry the step reports its **own existing** token with a new detail — `c-tests-failed:
    build-lock` and `c-faults-run: build lock` — so no new token name enters the gate. The lock directory
    lives inside the per-run results directory, which `tools/gate.sh` recreates for every run (`rm -rf` then
