## 1. Facts that bound the decision

- [OBS] `core/src/common/ivs_status.h` has `ivs_status` as `int`, `IVS_OK` 0, `IVS_E_BAD_ARG` -1, `IVS_E_BAD_STATE` -2. Comment: a refused call never mutates caller state; guest faults are not refusals (D-12).
- [OBS] Phase 2 D-06 reserved `core/include/ivs/` for the public header "until API-01"; `cp1610.h` is internal, "not installed and not an ABI".
- [OBS] Phase 2 D-03/D-07: state structs are plain, pointer-free, embedded by value, reserved bytes zero; no dynamic allocation anywhere in `core/`; the symbol allowlist (`tools/check/core-symbols-allow.txt`) has no allocator, and D-21 deferred "mutable-static-data detection" to Phase 3 API-01 and an "exported-symbols-match-prefix check" to later.
- [OBS] CPU state already has `IVS_CP1610_RS_UNRESET`; a step in UNRESET returns a NOT_RESET unit, 0 cycles, no change (D-12). The machine layer can reuse this as its pre-reset phase.
- [OBS] Profile `system_images.exec_grom`: required slot, digest bound at run time, different digest = different profile identity, supply policy pending D5. `cartridge.slots`: one slot, ROM-only decles. `power_on_fill.*`: zero by default, schema allows pattern/seeded.

- [OBS] Sibling host library (LibFuturo header): opaque `lf_instance`, `lf_create(profile_id, options, &out)`, `lf_destroy(&owned)`, `size_t struct_size` first in every request struct, optional allocator callbacks in create options, input bytes "borrowed only for this call", host serializes each instance. ## 2. Options for ownership and lifetime

| Option | Shape | Pros | Cons / footguns |
|---|---|---|---|
| A. Core-side allocation, opaque handle | `create(options{allocator callbacks}, &h)`, `destroy(&h)` | Matches the sibling host API; caller never sizes anything | Allocator failure becomes a new refusal with its own state effect; per-instance allocator context to thread through; double-free and ownership confusion; a core that calls caller callbacks has a re-entrancy surface; memcmp-of-everything refusal oracle is harder (heap pieces) |
| B. Caller-provided storage, opaque handle | `storage_requirements(profile_id) -> {size, align}`; `create(options, storage, size, &h)`; `destroy(h)` returns the storage to the caller | No allocator at all (fits "no alloc in core" literally); no allocation-failure class; instances can live in static memory, arena, stack, mmap; pointer-free flat instance is memcmp-able, relocatable by memcpy, and snapshot-friendly; trivial to wrap with `malloc` (host adapter) | Caller must size and align (guarded by checks); instance is fixed worst-case size (~150 KB for a 64K-word cartridge window, [INF]); strict-aliasing hazard if the caller hands a `static unsigned char[]` it also touches as bytes |
| C. Hybrid: B as primitive plus `ivs_machine_create_alloc(options with allocator)` convenience | Both | Easiest first-use ergonomics for C hosts | Two lifecycle paths to specify and test; allocator callback re-enters the host from inside the core; adds a refusal (`ALLOC_FAILED`) whose only purpose is the convenience |
| D. Global singleton (libretro-style single instance per process, [BG]) | No handle | Smallest API | Violates "multiple instances, no globals", makes API-01 isolation untestable; rejected |

Lessons [BG]: zlib `z_stream`/`inflateInit_` passes `stream_size` to catch header/library skew and has `zalloc/zfree`; Vulkan and Win32 carry a size or type tag in every struct and take allocator callbacks as an optional extra; SQLite and libretro show the cost of process-global configuration and a sticky last-error (here: forbidden, see D-A9). Anti-patterns to avoid: two-phase "create, then configure" leaving a half-built instance, enums as ABI types (width is compiler-defined), returning pointers into instance storage that dangle after the next load, host callbacks inside the core, errno-style last-error state.

## 3. Lens pass (condensed)

- Emulator/memory architect: the instance must be one flat, pointer-free struct (store the profile as an index, never a pointer to a profile table) so "refused load changes nothing" is a whole-storage `memcmp`, reset equivalence is a digest equality, and a relocated copy runs identically. Content is copied into instance storage, never borrowed past the call (no lifetime coupling to host buffers; later save states stay self-contained).
- Hardware/EE: a cartridge swap on a real console is a power event. Modelling every successful content change as a return to the power-on state avoids inventing hot-swap behaviour that no source documents ([UNK] hot-swap is undocumented; the model stays inside what is defined).
- QA: one table (status x call x state effect x test name) is the artifact; effects are checked by byte comparison, not by trusting prose; each refusal is a distinct named test; named faults prove the oracle bites.
- Security/rights: the API takes bytes only (no paths), never reads files, never logs bytes; the core reports length and digest and retains nothing the caller did not load. Input overlapping instance storage is refused. Rights-bearing images exist only in caller memory and the instance; nothing in the API encourages persisting them.
- DevOps/CI: every new check is shell/cmake/nm, well under a second; no new CI job, no cache, no matrix. It rides the existing `c-build`, `c-tests`, `c-purity` steps plus one tiny `api` step.
- API/integrator: the runner and the installed consumer need only create, load, reset, query, digest, destroy in Phase 3, and run in Phase 4. A versioned-struct rule and a runtime `ivs_api_version()` let a consumer detect header/library skew.
- Product/DX: names are guessable (`ivs_machine_*`), every call returns one status, outputs are defined on refusal, one doc page lists lifecycle and effects. The status name function gives the runner readable outcomes (RUN-02).

## 4. Recommendation (concrete sub-decisions; copy into CONTEXT as D-xx)

**D-A1 Ownership [REC].** Option B. The core never allocates; the host supplies storage. Public flow: `ivs_machine_storage_requirements(profile_id, &req)` then `ivs_machine_create(&opts, storage, storage_bytes, &m)`; the handle value equals the storage pointer. `ivs_machine_destroy(m)` scrubs the storage to zero and invalidates the handle; the host then frees or reuses the memory. No allocator callback in Phase 3; an allocating convenience may be added later as a pure addition (option C) without breaking anything.

**D-A2 Instance layout [REC].** One flat struct, no pointers, no `bool`/enum/bitfield, all reserved bytes zero, a magic word, a profile index (u32), a lifecycle phase, machine time, CPU state embedded by value (the 32-byte `ivs_cp1610`), RAM/GRAM/STIC/PSG state, slot records, and content storage at the profile's worst-case capacity. The type is incomplete in public headers (`typedef struct ivs_machine ivs_machine;`); the definition lives in `core/src/machine/`. `create` zero-fills the whole storage first, so unused bytes are deterministic. Required alignment is reported by the requirements call (16 bytes recommended); misaligned or undersized storage is refused.

**D-A3 Create inputs [REC].** `ivs_create_options { uint32_t struct_size; uint32_t flags /*must be 0*/; const char *profile_id; }`. Profile id is exact, case-sensitive, NUL-terminated ASCII, scanned to a bound of 64 bytes; unknown id gives `IVS_E_UNKNOWN_PROFILE`. No clock, seed, fill pattern, path or allocator in options: those are profile data or host concerns. Power-on fill comes from the profile record only. The profile table is generated at build time from `data/profiles/*.json` (shared with MEM-01) and is `const`.

**D-A4 Struct versioning [REC].** Every in/out struct of the public API starts with `uint32_t struct_size` (fixed width, not `size_t`). Callee rule: `struct_size` below the v1 minimum gives `IVS_E_BAD_ARG`; a larger size is accepted only if the trailing bytes it does not know are all zero, else `IVS_E_UNSUPPORTED`; fields beyond a smaller caller struct read as zero/default. Out structs: the callee writes only `min(caller size, own size)` bytes and sets `struct_size` to what it wrote. Reserved/flag fields must be zero (nonzero gives `IVS_E_UNSUPPORTED`). Plus `IVS_API_VERSION_MAJOR/MINOR` macros and `uint32_t ivs_api_version(void)` (packed major.minor) so a consumer asserts header == library. Pre-1.0 means no ABI stability promise; the mechanism exists so additions do not break.

**D-A5 Lifecycle and content semantics [REC].**
- States: after create, phase UNRESET (CPU run state UNRESET, machine time 0, all slots empty, volatile state at profile power-on fill). After a successful reset, phase RESET.
- `ivs_machine_load(m, &req, &res)`: one typed image per call (`kind` is one of EXEC, GROM, CARTRIDGE; a boot-stub kind is added only if the D5 point chooses it). Bytes are borrowed for the call and copied in; the call is all-or-nothing: validate fully, then commit. Loading into an occupied slot replaces it atomically (no SLOT_OCCUPIED code: refuse-then-unload would create a window with no content). A cartridge import is one call with the whole image, so multi-segment atomicity needs no extra API.
- `ivs_machine_unload(m, kind)` empties that slot (and zero-scrubs its storage). Unloading an already empty slot is a successful no-op (like `free(NULL)`).
- Rule C (content change = power event): any successful load or unload returns volatile state to the power-on fill, CPU to UNRESET, time to 0, phase UNRESET. So machine state is a function of (content set, reset count), and "create + loads in any order" equals "create + same final content".
- `ivs_machine_reset(m, kind)`: kind `IVS_RESET_POWER_ON` only in Phase 3 (a warm reset that keeps RAM is reserved; any other value gives `IVS_E_UNSUPPORTED`). It refuses `IVS_E_MISSING_SYSTEM_IMAGE` if the profile's required system images are not present (final policy per the D5 point; this API point only fixes that the check lives at reset, the first moment the machine is asked to start, so load order is free). Success: volatile state to power-on fill, CPU reset sequence armed, time 0, phase RESET, content slots untouched.
- Reset equivalence invariant (tested): digest after (run, reset) == digest of a fresh instance with the same content after reset.
- `ivs_machine_destroy(m)`: validates the handle, zero-scrubs the whole storage (so a later stale call fails magic check, best-effort), returns `IVS_OK`. Destroy has no refusal that touches storage: a bad handle is `IVS_E_BAD_HANDLE` with no write.

**D-A6 Queries [REC].** `ivs_machine_info(m, &info)` (versioned struct): profile id (pointer to static const string), phase, per slot `{present, length_units, unit_bits, digest[32], algorithm}`. A load result carries the same length and digest of the image just committed (MEM-03). Digest algorithm and canonical serialization belong to another point; here only: a digest struct is `{uint32_t algorithm; uint8_t bytes[32]}` so the algorithm is named in the value. `ivs_machine_state_digest(m, &d)` returns a digest of a canonical little-endian field-by-field serialization (not raw struct bytes, which would tie goldens to layout, padding and host endianness); Phase 4 adds per-domain digests behind the same function with a `domain` argument already reserved as a `uint32_t` that must be 0 in Phase 3. The refusal tests use raw whole-storage `memcmp` as the strict oracle and the canonical digest as the public-facing one.

**D-A7 Status taxonomy [REC].** Keep `ivs_status` = `int`, 0 = OK, negative = refusal, positive unused (reserved). Numbers are frozen once merged (append-only; never renumber or reuse). Keep -1 and -2; add by class:
- General: -1 `BAD_ARG` (null, misaligned, bad struct_size, out-of-set enum, unterminated id, input overlapping instance storage), -2 `BAD_STATE` (kept; used only where a call is invalid in the current phase, none in Phase 3 beyond future run), -3 `BAD_HANDLE` (null, wrong magic, destroyed), -4 `UNSUPPORTED` (well-formed but not implemented: unknown nonzero flag, reset kind, newer struct tail), -5 `BUFFER_TOO_SMALL` (storage smaller than required; out field `required`; Phase 4 reuses for output buffers, API-04).
- Content: -16 `UNKNOWN_PROFILE`, -17 `MALFORMED`, -18 `OVERSIZED`, -19 `OVERLAP`, -20 `OUT_OF_RANGE`, -21 `MISSING_SYSTEM_IMAGE`; -22..-31 reserved for D5 outcomes (for example a pinned-digest mismatch via a reserved `expected_digest` request flag).
- Each matrix row of MEM-04 maps to exactly one code. A coarse code can carry a `uint32_t detail` (sub-reason such as "bad magic", "truncated", "bad checksum") and a `uint64_t offset` in the load result; both are defined only on refusal, with stable numbers listed in the same table. No errno-style last-error and no per-instance error field: a refusal must not write instance bytes (D-A9).
- Classes stay separate: caller refusal (negative status), guest fault (CPU sticky fault, reported through run results, never a status), internal invariant violation (`__builtin_trap()`, never a status).
- `const char *ivs_status_name(ivs_status)` returns a static string (`"IVS_E_MALFORMED"`), `"IVS_E_UNKNOWN"` for unlisted values; a switch, no libc.

**D-A8 State-effect documentation, machine-checked [REC].** New source of truth `data/api/api-effects.json`: a `calls` array (name, header, `on_ok` prose id) each with `refusals: [{status, effect, outs, test}]`, where `effect` is `none` or an id in an `effects` registry (name + one-sentence definition), `outs` is how out parameters look on refusal (always "zeroed" except `required`/`detail`/`offset`), and `test` is the test id. Policy: every Phase 3 refusal has effect `none`; a named partial effect is allowed only for calls whose contract is progress (the Phase 4 run) and needs a registry entry. A `sh`/`cmake -P` step `api` (about 0.1 s) checks: (1) every `#define IVS_E_*`/`IVS_OK` in `ivs/ivs_status.h` equals a line of the frozen list `data/expected/api-statuses.ids` (`NAME VALUE`) and vice versa; (2) every `IVS_API` declaration in `core/include/ivs/*.h` is in `data/expected/api-calls.ids` and in the JSON, and vice versa; (3) each (call, status) row names a test id present in `data/expected/tests/api.ids` (tests-inventory already proves the test ran); (4) every effect is `none` or registered; (5) every status except OK appears in at least one row (no dead codes), and every status named in the docs exists. Test naming convention `api.<call>.<status-short>` makes coverage a name check.
- Test oracle for `none`: the harness helper snapshots the whole storage before the call and `memcmp`s after; it also asserts the out struct is zeroed except the allowed fields.
- Named faults (D-18 pattern): `IVS_FAULT_LOAD_MUTATE_FIRST` (load writes the slot before validating), `IVS_FAULT_STATIC_SHARED` (a function-static counter touched by create/step), `IVS_FAULT_DESTROY_NO_SCRUB`, `IVS_FAULT_LOAD_SETS_LASTERR` (writes an error field); each must be caught by exactly the intended test.
- Negative controls under `tools/check/controls/`: `api-status-renumbered`, `api-status-undocumented`, `api-call-missing-from-table`, `api-call-missing-from-header`, `api-refusal-without-test`, `api-effect-unregistered`, `api-dead-status`, `core-static-mutable` (stand-in core with a writable static).

**D-A9 Refusal purity [REC].** A refused call writes only its out parameters. The instance holds no last-error, no counters of refusals, no timestamps. (This is what makes `memcmp(before, after) == 0` the complete oracle.)

**D-A10 Thread-safety and re-entrancy contract [REC].** Distinct instances are fully independent and may be used from different threads with no locking. One instance must not be used concurrently; the host serializes (same stance as the sibling API). The core has no globals and no mutable static data, creates no threads, takes no locks. The public API has no function-pointer parameters (no host callbacks), so there is no re-entrancy path; CPU bus callbacks stay internal. Shared state is `const` tables only. Enforcement: (a) new `c-purity` sub-check "no writable data symbols" over the release (non-PIC, non-sanitizer) archive: after filtering `ltmp*`/`l_*` labels, fail on nm types `d D b B c C s S` that are writable for the platform [UNK: the exact letter set per platform needs a spike; Darwin `s` is ambiguous, so a section-based `size -m`/`objdump -h` variant may be needed]; sanitizer variants use `--allow-prefix`; (b) behavioural isolation test: two instances with different content, interleaved steps, equal to each instance run alone; (c) relocation test: `memcpy` an instance to a second buffer, drive both identically, digests equal (catches self-pointers).

**D-A11 Header layout, naming, export [REC].** Public headers in `core/include/ivs/`: `ivs.h` (umbrella plus version), `ivs_status.h` (moved from `core/src/common/`, internal includes become `"ivs/ivs_status.h"` with `core/include` on the include path), `ivs_machine.h`. Public headers use only `<stddef.h>` and `<stdint.h>`, carry `extern "C"` guards, `#define`d constants (no enums), and the `IVS_API` macro on every function (empty on static builds; `__attribute__((visibility("default")))` or `__declspec(dllexport/dllimport)` for a future shared build). Prefix: functions `ivs_`, macros `IVS_`, types `ivs_`; never "intellivision". CPU headers (`cp1610.h`) and machine internals stay in `core/src/` and are never installed. Phase 3 ships a static library only; shared-library packaging is a Phase 4 choice. The deferred exported-symbols check is satisfied by the `IVS_API` list equality (D-A8 step 2) plus a CTest that compiles each public header alone in a C17 TU (`-Wall -Wextra -pedantic`) and a trivial `-x c++` include check where a C++ compiler exists (skip visibly, never silently).

**D-A12 Minimal Phase 3 surface [REC].** Public, 10 functions: `ivs_api_version`, `ivs_status_name`, `ivs_machine_storage_requirements`, `ivs_machine_create`, `ivs_machine_destroy`, `ivs_machine_reset`, `ivs_machine_load`, `ivs_machine_unload`, `ivs_machine_info`, `ivs_machine_state_digest`. (Profile listing and map dump stay internal or tooling.) Not public in Phase 3: any run/step call, memory peek/poke, input, video/audio buffers, snapshots. The isolation test (success criterion 5) drives stepping through an internal seam `ivs_machine_step_unit_internal(m, &result)` declared in `core/src/machine/machine.h` and linked only by tests; Phase 4 builds the public `ivs_machine_run(target_tick)` on it. The decode-table dump (MEM-01) is likewise an internal generated dump compared against the sourced literal map, not an API. Extension points for Phase 4 without breakage: new functions, new `kind`/`domain`/`flags` values, struct tails guarded by `struct_size`, status codes appended in reserved ranges, `ivs_machine_info` growing.

**D-A13 Phase 4 consumers [REC].** The runner and the installed consumer include only `ivs/ivs.h` and link `ivs::core` (static, exported by `install(EXPORT)`, [INF] consistent with D1 and the sibling `find_package` idiom). The runner target gets only `core/include` on its include path (a build-level guarantee it cannot reach internals). Phase 4's relocated consumer calls requirements, create, load (with an original stand-in image), a refused load with a name lookup, reset, digest, destroy, and checks `ivs_api_version()` against the header macro. Host policy such as file reading, allocation, wall time and reporting lives in the runner.

## 5. Adversarial pass against D-A1..D-A13

1. "Fixed worst-case instance size wastes memory and hurts fuzzing/many instances." True: about 150 KB per instance if the cartridge window is a full 64K words [INF, to be measured]. Mitigation: size comes from the requirements call, so a later profile or an optional `cartridge_capacity` create field can shrink it without an API break. Cost accepted; no evidence that more than a few instances are needed in this milestone.
2. "Caller storage invites misuse (wrong size, alignment, reuse after destroy)." Checked by size/alignment/magic, all with typed refusals. Residual: strict aliasing if a host passes a declared `static char` buffer and also touches it as other types, and use-after-free of the storage itself, which no API can detect. Mitigation: document "allocator memory or an aligned buffer not otherwise accessed", test both malloc and an aligned static buffer in the `release -O2` test, no LTO in core.
3. "Opaque + allocator is the sibling convention, so the adapter will be awkward." The adapter only needs to call the requirements function, allocate through its host allocator and call create: five lines. Reverse direction (B over A) is impossible without an allocator. B costs nothing ABI-wise because callers never see the struct either way.
4. "Rule C (every content change is a power-cycle) surprises frontends that hot-swap." It is explicit, testable and matches the reset a human does after a swap; a future `warm` option can relax it additively. It does remove any need to define behaviour for content changing under a running CPU.
5. "Reset refusing for missing system images conflicts with MEM-04 wording, which lists missing-system-image among load refusals." Real tension. Under this design a cartridge load never refuses for missing EXEC (load order free); the refusal is at reset. If the D5 point decides that a system-dependent cartridge load must refuse at load time, `IVS_E_MISSING_SYSTEM_IMAGE` is simply also returned by `load`; the code and table accommodate both. The refusal-matrix test must assert whichever D5 chooses. Flagged as the coupling to resolve in the synthesis.
6. "Refusal-with-no-effect plus no last-error makes debugging hard." The `detail`/`offset` out fields and `ivs_status_name` give diagnostics without instance state.
7. "A machine-checkable table is over-built." It is one JSON file, one ~60-line cmake script, ids lists that mirror existing patterns; the alternative (prose effects) is exactly what API-06 forbids and what silently rots. Throwaway-level cost, recurring failure class (a new refusal added without a documented effect or test).
8. "Moving `ivs_status.h` churns Phase 2 includes." One mechanical edit across cpu files and tests; the gate and tests catch a miss. Alternative of a forwarding internal header leaves two spellings; not recommended.
9. "The nm writable-data check may false-positive on Linux PIC const pointer tables." Applied only to the non-PIC release archive; if it still misfires, fall back to a section-based check. Marked [UNK] with a plan-time spike (about 30 minutes), not a blocker for the design.

## 6. Top risks

1. The decle/GROM/EXEC byte layout of load inputs and the cartridge format are not fixed here; the `load` request carries only `kind` + bytes, so those points must define container layouts, length units and the `detail` registry before the table can be finished.
2. D5 timing of the missing-system-image refusal (load vs reset) may change which function owns `IVS_E_MISSING_SYSTEM_IMAGE` and therefore the matrix; the status table is robust to either, the test names are not.
3. Writable-static detection portability (Darwin vs Linux gcc) and the strict-aliasing/lifetime footgun of caller storage; both are caught only partly by tooling and rely on tests across sanitizer and `-O2` builds.

## 7. What would reverse it

- A concrete host binding (Elixir NIF resource, Python ctypes, WASM) or the LibFuturo adapter showing that caller-provided storage is materially harder than an allocator callback: add option C's convenience (additive), not a redesign.
- Instance size becoming multi-megabyte (bank-switched or large cartridges, snapshots stored inline): move to per-create capacity or an allocator.
- Evidence that real hardware content swap preserves RAM/state in a way a profile needs: add warm-swap kinds, relax Rule C.
- A need for host callbacks in the core (for example streaming content): reopens the re-entrancy contract.
