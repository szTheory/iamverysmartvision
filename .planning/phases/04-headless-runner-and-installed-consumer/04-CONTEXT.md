<domain>
## Phase Boundary

An original, project-authored diagnostic runs from reset through the public API, the headless runner and an independently built installed consumer. Digests are deterministic, failures are reported honestly by kind, and the CI gate mirrors the local command.

In scope: API-02, API-04, RUN-01, RUN-02, RUN-04, RUN-05, RUN-06, PKG-01, PKG-03, PKG-04 (and the D4, D6, D12 decisions).
- `ivs_machine_run` (absolute master-tick target, overshoot, stop reasons), public read-only guest observation, output-buffer contract with zero-length video/audio, input-event plumbing and the input-log digest, digest domains VIDEO/AUDIO/INPUT.
- `ivs-run` runner, IVSS scenario format, report format, outcome taxonomy and exit codes.
- Project boot stub, first original diagnostic cartridge, hand-assembled annotated listings and their checker, goldens with tier/oracle headers.
- CMake install/export of the static `ivs::core`, relocatable package, independent consumer, `pkg-install` gate step.
- CI summary, run-record file, `important-gates` coverage, budget rule, branch-protection recommendation, release design (deferred implementation).

Not in scope: real STIC/PSG/GROM/controller device behaviour and the control-to-byte table (Phases 5-7), frame events, a shared library, shipping the runner in the install package, a macOS CI leg, release workflow implementation, any assembler as a dependency.
</domain>

<decisions>
## Implementation Decisions

### Public run API and observation (API-02, API-04)

- **D-01:** One call: `ivs_status ivs_machine_run(ivs_machine *, const ivs_run_request *, ivs_run_report *)`. The absolute target is in MASTER TICKS (D2); CPU-cycle and frame forms are runner sugar. It runs `while now < target: step one unit`, ends at the first unit boundary `>= target`, and keeps no state between calls (no budget, no deficit, no pointer). `run(now + 1)` is the single-step idiom; `ivs_machine_step_unit_internal` stays internal.
- **D-02:** Request: `struct_size`, `flags` (`IVS_RUN_F_STOP_ON_HALT = 1`; `2` reserved for a frame stop, UNSUPPORTED until Phase 6), `target_ticks` (values above 2^63 are OUT_OF_RANGE), the input array (D-17), and video/audio buffer pointer plus capacity.
- **D-03:** Report: `stop_reason`, `refusal_reason`, `cpu_run_state`, `cpu_fault_reason`, `now_ticks`, `overshoot_ticks = max(now - target, 0)`, `elapsed_ticks`, `units_executed`, the input fields of D-17, `video_frames_completed`, `video_bytes_written`, `audio_bytes_written` (the last three are 0 in Phase 4). Overshoot is derived, not state.
- **D-04:** Stop reasons are append-only and pinned by `data/expected/api-stop-reasons.ids`: `TARGET=1`, `CPU_HALTED=2` (only with the flag), `GUEST_FAULT=3`, `INTERNAL=4` (step refused or no progress; the runner maps it to harness failure). The reason is a pure function of exit state (fault, then halt, then target). A guest fault is `IVS_OK` plus a stop reason (D-12 of Phase 2 stands). `ivs_run_stop_name()` is added.
- **D-05:** Refusal order for run, each with effect `none` and a row in `data/api/api-effects.json`: BAD_ARG, BAD_HANDLE, report-overlap BAD_ARG (A-08 style, uintptr_t), UNSUPPORTED, buffer/event argument BAD_ARG, BAD_STATE (machine is OFF), OUT_OF_RANGE, BUFFER_TOO_SMALL (before any step), then input order/channel BAD_ARG. No new status numbers; new reasons start after the existing load-report reasons.
- **D-06:** API-04 is testable now with zero-length real video/audio (layout format NONE, sizes 0, no fabricated frame). The public call wraps an internal env seam `ivs_machine_run_env_internal` that takes the output layout and channel table, so tests use a synthetic layout to prove: undersized capacity gives BUFFER_TOO_SMALL with whole-storage `memcmp` equality, exact fit is OK, overlap and NULL cases refuse. Output layout and timebase (ticks per CPU cycle, nominal frame ticks) are appended to `ivs_info`; no new functions.
- **D-07:** Slicing invariance: the whole instance is the resumable state. Target must never reach a unit, a device catch-up or a flush. The test replays stand-in programs (HLT and guest-fault variants) under five slicing patterns against a unit-by-unit reference trace and compares CPU digests at every boundary, the composite and all domain digests at sampled ends, whole-storage `memcmp`, and summed counters. It must run on the real diagnostic every phase. Named faults: `RUN_BUDGET_CARRY`, `RUN_STOP_BEFORE_OVERSHOOT`, `RUN_EVENT_AT_TARGET_ONLY`, `RUN_CAPACITY_AFTER_STEP`, `RUN_TARGET_UNCHECKED`, `RUN_FAULT_STEPS` (planning finalizes the list).
- **D-08:** Public read-only guest observation: `ivs_machine_cpu_state(const ivs_machine *, ivs_cpu_state_report *)` and `ivs_machine_peek(const ivs_machine *, uint16_t addr, uint32_t count, uint16_t *out)`. Both are side-effect-free by contract (no time advance, no gate/stub side effect, reads through a non-mutating view of the memory map), refused before any write, with effect-table rows and faults `PEEK_ADVANCES_TIME`, `PEEK_GATE_IGNORED`. `ivs_machine_run_env_internal`, access logs, breakpoints, callbacks and the memsys stay internal.
- **D-09:** Frame and CPU-cycle bounds are runner sugar: `frames N` means `N * nominal_frame_ticks` and is printed as "nominal, not frame events". Cancellation and wall-clock timeout live only in the runner, as slices of `run()`.

### Digests and goldens (RUN-05)

- **D-10:** Digest domains 16/17/18 become VIDEO/AUDIO/INPUT, each a `chain[32]` + `count u64` row inside the instance, cleared at create and at reset, domain version 1. The composite digest stays version 1 over domains 1..4, so no Phase 3 literal changes (pin a Phase 3 composite literal first); per-domain digests of 16..18 are reported individually. Chain rule for video/audio: `SHA256("IVSR" || domain || chain || index || len || record)`; the INPUT chain is D-18.
- **D-11:** Goldens come in two kinds. `*.expect` holds predicates (tier `original-diagnostic`, oracle `independent-derivation`, with derivation cites). `*.digests` holds digests (tier `deterministic-repeatability`, oracle `self-recorded`). A gate checks the header: `self-recorded` forces the repeatability tier, and domains with no content are marked `none`/`absent`, never `observed` or a hash of nothing. Goldens are updated only by an explicit runner `--update-golden` helper.

### Input and D6 (INP groundwork, API-03 mechanism)

- **D-12 (D6, delegated decision):** Core input is LOGICAL switch state: one `uint32` per controller, index = PSG port (0 = R14/$01FE, 1 = R15/$01FF), never player/left/right. Bits: 12 keys bits 0-11, 16 disc positions one-hot bits 12-27 clockwise from north, 3 side codes bits 28-30 (the two top buttons are one code, C15), bit 31 reserved (nonzero is UNSUPPORTED). The electrical active-low port byte is a DERIVED read-only observation computed in-core from profile data in Phase 5; there is no raw-byte override and no electrical input path. The research agent for the run API recommended electrical-per-port; the controller agent's logical choice wins (lossless replay, one source of truth, ambiguity handled in one tested place). Reversal: evidence that the controller output is not a function of switch state plus port drive, or a consumer needing raw port injection (then a flag-gated event field).
- **D-13:** Input is delivered as a caller-owned, nondecreasing-by-tick array of level samples carried in the run request: `ivs_input_event` (32 bytes: `u64 at_tick` in master ticks, `u32 flags`, `u32 reserved`, `u32 controller[4]`; words 2-3 reserved for expansion and UNSUPPORTED if nonzero on the 2-controller profile). The core retains nothing: no stateful `set_input`, no instance queue.
- **D-14:** An event takes effect at the first CPU-unit boundary whose start tick is `>= at_tick`. The report returns `input_consumed`, `input_floor_tick` (start of the last begun unit + 1) and `controller_now[4]`; the host resubmits the unconsumed suffix. Events below the floor, unsorted, or `>= 2^63` are BAD_ARG; reserved bits/flags/extra words are UNSUPPORTED; the whole array is validated before any write; the failing index and reason go in the report; new `IVS_REASON_*` values only.
- **D-15:** The INPUT digest domain is live in Phase 4: rows hold the words in force, the applied count and a chain `h(n+1) = SHA256(h(n) || be64(tick) || be32 words)` with `h0 = SHA256("IVS-INPUT-LOG-V1")`; reset clears it. The logical plumbing is real in Phase 4 (RUN-01's input schedule and RUN-05's input-log digest need it); only the control-to-byte table and the PSG R14/R15 reads wait for Phase 5. The profile gains only `input.controllers`; the real profile registers no consumer of input in Phase 4 so input is guest-invisible until Phase 5.
- **D-16:** Record: C14 decided, C15 modelling choice, new discrepancy entries (disc internals, unplugged/upper-byte read, output-driven port read, which connector is R14, unit-start granularity of input application) each with a D10 resolver. Tests now: bit-name inventory `data/expected/input-bits.ids` against the header, refusal rows with digest unchanged, slicing fuzz including events inside the overshoot window, independent cmake-sha256 oracle for the chain, reset, isolation. Named faults: `INPUT_APPLY_AT_RUN_START`, `INPUT_LOG_SLICE_RELATIVE_TICK`, `INPUT_NO_FLOOR_CHECK`, `INPUT_STATIC_CARRY`.

### Runner (RUN-01, RUN-02)

- **D-17:** Layout `runner/`: `ivs_runner_lib` (parser, executor, report, outcome mapping, host vtable), thin `main.c`, `hostio.c`. Executable `ivs-run` (target `ivs_run`), links only the public `ivs_core`, built in both presets. One process runs one scenario on one fresh instance; no globals except the signal flag.
- **D-18:** Scenario format IVSS v1: line-based directives, no quoting, `ivss 1` first. Directives: `id`, `profile`, `content <exec|grom|cart> <relpath>|user|boot-stub|zero-grom`, `expect-load`, `expect-sha256`, `run-to <n> ticks|cpu-cycles|frames [stop target|halted|faulted]`, `assert <subject> ==|!= <value>` (checkpoints; subjects from D-08: `halted`, `reg R3=0037`, `mem 0200=7FFF`, `mem A..B=...`, `digest <domain>=...`), and `input at_tick=|at_cycle= c0=<names|0xHEX> c1=...` (names pinned by D-16). No `at_frame` until Phase 6.
- **D-19:** Report: flat `key value` lines in fixed key order; first line `ivsr 1`, last `report.end <n>`; no wall time, no host paths. Goldens carry `# tier:` and `# oracle:` headers.
- **D-20:** Exit codes: pass 0, guest-fail 10, timeout 11 (`budget` or `wall`), cancelled 12, missing-fixture 13, harness-fail 14 (avoid ASan's default 1, ctest skip 77, shell 126+). Each outcome has a fixed precedence and one demonstrating scenario listed in `data/expected/runner-scenarios.ids`.
- **D-21:** Timeout and cancellation live only in the runner: slices of at most `1<<22` ticks, a `sig_atomic_t` flag and the monotonic clock checked between slices; machine-time budget (deterministic, golden-able) is separate from the wall watchdog (host-dependent, never golden); a scenario may only lower the wall cap; `--max-ticks` is a ceiling. Deterministic test hooks `--self-signal-after-slices N` and `--wall-timeout-ms 1`; no sleeps or racing signals in tests.
- **D-22:** Scenarios are untrusted inert data. Paths are relative `[A-Za-z0-9._/-]` without `..`, resolved under `--content-dir`; a scenario cannot name output files. System images come only from operator `--exec/--grom/--cart`. Reads are bounded at cap+1 and only regular files. Caps: scenario 64 KiB, 512 lines, 256 bytes per line, 64 asserts, 64 steps, storage 64 MiB, buffers 8 MiB, default wall cap 30 s.
- **D-23:** Tests: suite `runner` (in-process with a fake host vtable: parser table, seeded fuzz, slicing invariance, named faults) and suite `runner-process` (a shell TAP script running the real executable: dev vs release output byte-for-byte, slice variants, cwd independence, judge self-controls). Both use existing inventories and `skip-ok`; no new workflow step. `_POSIX_C_SOURCE` only in `hostio.c`; `signal()` not `sigaction`; POSIX sh and dash safe; run `tools/gate-linux.sh` before the first runner push.
- **D-24:** The runner is NOT in the install package and the installed consumer does not need it; the gate compares the consumer's printed digests with the runner golden for the same scenario. Generalize the named-fault framework (`tests/faults.cmake`, the `faults-verdict` site scan) from core-relative to repo-relative owner TUs so runner faults fit.

### Diagnostic, boot stub and D4 (RUN-06)

- **D-25 (D4, delegated decision):** Diagnostics are HAND-ASSEMBLED annotated decle listings; the listing is the source of truth. No assembler is a build, gate, CI or release dependency. `as1600` is rejected (GPL-2.0+, SDK `.asm` includes). `libasm` is an optional non-gating black-box cross-check recorded as an executed result only. A project mini-assembler is deferred until more than 3 diagnostics, labels/macros, or a second author (trigger recorded; the ~400 asm/program pairs in the Phase 2 vectors are its future test corpus).
- **D-26:** Listing lines: `<ADDR> <hex4> <bit groups> <ROW|-> <asm>`. A new check `tools/check/listing.cmake` (copying the vector checker's hex-equals-bits and row-leaf rules) covers listings, with one negative control per token.
- **D-27:** The oracle is arithmetic and manual tables, not a second interpreter: 16-bit addition, the sum 1..10 = `$0037`, the GSWD layout (pdf 56), stack direction (C17), and the printed cycle table. The predicate is 10 memory words, R0-R5 plus R6, and stop reason `halted`; R7, flags at halt and machine time are excluded on purpose. The claim (CL-0008) stays provisional; shared-misreading risk is recorded.
- **D-28:** Boot stub: a 22-word text listing at `$1000-$1015` in `fixtures/FX-boot-stub/`, manifest note "project boot stub, not an EXEC". Reset vector `B $1010` at `$1000`; interrupt trap at `$1004` (unexpected-interrupt: MVII, MVO to `[035F]`, HLT, TSTR R0); reset code at `$1010`: `DIS; MVII #$0340,R6; J $5000`. The EXEC image is built into the build tree; nothing binary is committed.
- **D-29:** Anti-HLE guards: addresses stay within `$1000-$101F`, at most 16 non-zero words; allowed rows only HLT, DIS, EIS, MVII, MVO, TSTR, B, J; words must exist at the profile's `reset.r7` and `interrupt.iab_value` locations; path tests expect R7 = 1000, 1010, 1011, 1013, 5000 and a trap test that pulses INTR once; a no-routines, no-services review rule in `docs/diagnostics.md`. HLT stops only after the next instruction and only at an interruptible boundary, so every stub or diagnostic ending needs a TSTR follower (zero fill is not a trap).
- **D-30:** The core stays image-free. A small C tool `tools/pack` builds the EXEC image and the `.ivsc` in the build tree (cmake -P cannot write NUL bytes). The runner derives the label only from the symbolic content name `boot-stub` and prints `exec: project boot stub, not an EXEC sha256=...`. Because reset also requires GROM, the runner synthesizes 2048 zero bytes named `zero-grom`, labelled "not a GROM"; nothing committed.
- **D-31:** The cartridge `ivs-diag-cpu-1` is one IVSC segment at `$5000`, 56 words, covering flags (INCR vs ADDI, GSWD), a loop summing 1..10 = `$0037`, a PSHR/PULR round trip and an indirect `MVI@` with auto-increment; the end marker `[020F]=$03C5` is written last; it ends `HLT; TSTR R0 x3`. Tier `original-diagnostic`, manifest `FX-diag-cpu-1` (listing committed, `.ivsc` built, never committed), golden `data/golden/diag-cpu-1.golden`. The `$5000` entry convention and `$0340` stack have no source: log a new discrepancy (Phase 6/7 may change them; stub versioning).
- **D-32:** RUN-04 controls for the diagnostic mutate inputs (the fault registry allows each fault id in one file): program mutations (ADDI to SUBI, BNZE to BZE, PSHR to MVO@, INCR to DECR) must end `guest-failure` naming the right clause; outcome controls cover guest-failure, timeout, missing-fixture, golden-mismatch and harness-failure.

### Packaging and the installed consumer (PKG-01)

- **D-33:** Export one static target `ivs::core` (EXPORT_NAME core; in-tree ALIAS). Include dirs are `$<BUILD_INTERFACE:core/include>` and `$<INSTALL_INTERFACE:include>`; no absolute path in the export. Layout: `lib/libivs_core.a`, `include/ivs/*.h`, `lib/cmake/ivs/{ivsConfig,ivsConfigVersion,ivsTargets,ivsTargets-<cfg>}.cmake`, `<docdir>/LICENSE`. Pin `CMAKE_INSTALL_LIBDIR=lib`. Hand-written Config, `SameMinorVersion`, `ARCH_INDEPENDENT`, no `export(PACKAGE)`, no `.pc`.
- **D-34:** One version source of truth: the `IVS_API_VERSION_*` macros in `ivs.h`, parsed before `project()`; the consumer ties `ivs_VERSION`, `IVS_API_VERSION` and `ivs_api_version()` together. Install from the `release` preset tree that `c-build` already built (no third build); a sanitized tree refuses to install. `POSITION_INDEPENDENT_CODE ON` on the core objects.
- **D-35:** Static only; `IVS_API` stays empty (a shared link of the current archive exports zero symbols: define `IVS_API` before ever going shared). The runner is not installed. CMake floor stays 3.25 (tested on 3.28.3 and 4.4.3).
- **D-36:** The consumer lives in `tests/installed-consumer/`, unreachable from the root CMake. The step copies it outside the repo and builds it with `find_package(ivs 0.1 CONFIG REQUIRED)`, strict flags, `NO_SYSTEM_FROM_IMPORTED ON`, registry lookups disabled and path env vars unset in a subshell.
- **D-37:** New gate step `pkg-install` (about 2-3 s): install, `mv` into a path containing a space, DELETE the original prefix, then check. All temp files under `mktemp`; only `build/gate/pkg-consumer.txt` is kept. "Clean and independent" is proved from outputs: (a) the prefix equals `data/expected/pkg-install-files.ids` exactly (also the rights guard); (b) installed headers `cmp`-equal source headers and the archive sha256 equals the build-tree archive; (c) no `$ROOT/core|build` string in installed files or archive; (d) `ninja -t deps` shows every header under the moved prefix, with a positive-presence check; (e) the link line names the prefix archive and `ivs_DIR` is under the prefix.
- **D-38:** Symbol rules: every `IVS_API` name in the installed headers is defined in the installed archive; that set equals the `api-effects.json` call names; every external definition matches `^ivs_`. Installed headers compile alone as C17 and C++17 (visible SKIP without a C++ compiler; reuse `headers-tap.sh` with an include-dir argument) plus a direct C++ link of a tiny main.
- **D-39:** The consumer exercises create, load (boot stub plus the diagnostic cartridge), refusal (duplicate load, truncated EXEC, digest unchanged), reset, bounded run, per-domain digests, and a second fresh instance that must match; output is byte-compared with `data/expected/pkg-consumer.golden` ("regression pin, emulator is oracle") and its digests must equal the runner golden for the same scenario; `data/expected/pkg-consumer-calls.ids` pins which `ivs_*` names it references. The consumer obtains the boot stub and cartridge images from the build-tree `tools/pack` output via files passed as arguments (never from the source tree).
- **D-40:** Ten in-step selftests (`pkg-selftest=n/n`, purity-selftest style) mutate: a core/src include, a leak-detector bypass (`-I core/src`), a missing archive member, a ghost header declaration, an unprefixed symbol, a stray file in the prefix, a baked path, a refused version (0.2 and 1), a deleted old prefix, and golden drift.

### CI shape D12, measurement and gate evolution (PKG-03, PKG-04, RUN-04)

- **D-41 (D12, delegated decision):** Keep `pull_request` + `push: main`, one job `gate` on ubuntu-24.04, no matrix, no path filters, cancel-in-progress for PRs only, `timeout-minutes` 5. No macOS leg (core is a static lib; hosted-only bugs so far were gcc/Linux; reverse on an Apple-only failure reaching main, a shared lib, or a macOS contributor path). `tools/gate-linux.sh` stays local.
- **D-42:** `tools/gate.sh` writes the job summary through an EXIT-trap helper `tools/check/ci-summary.sh`: only when `$GITHUB_STEP_SUMMARY` is set, prints nothing to stdout, never changes the exit status. Contents: headline tokens, a "Skips and missing" table (every token matching skipped|missing|pending|unknown, "none" when zero), the 8 slowest steps, the first 40 FAIL lines in a fence. Annotations carry token names only.
- **D-43:** No artifacts and no caches, enforced structurally: `ci-parity` gets an action allowlist (`actions/checkout` only) and new tokens for `secrets.`, `strategy:` and `runs-on` other than `ubuntu-24.04`, each with a control. Posture unchanged: `contents: read`, SHA-pinned action, `persist-credentials: false`, `pull_request` not `pull_request_target`, no secrets.
- **D-44:** PKG-04: gate.sh adds `gate-env ncpu=.. cc=..` and `gate-cpu user=.. sys=..` (POSIX `times`) lines. An orchestrator-only `tools/ci-record.sh <run-id>` (2 `gh` calls per run; executors never call `gh`) appends to a new `.planning/ci-runs.tsv`; a new `ci-log` step validates the TSV format, with controls. Queue time cannot be measured in-job.
- **D-45:** Budget rule: apply the next lever when the median of the last 3 hosted gate-times exceeds 40 s; revisit the budget when any run exceeds 60 s or the median of the last 5 exceeds 50 s (same-code runs spread 38-49 s). Levers in order: keep Phase 4 steps cheap by construction (consumer installs from `build/release`), background `c-build` for independent steps only if `gate-cpu` shows idle cores, cut control-runner CPU, ccache (banned while within budget), a two-job split (last resort; redefines PKG-02). Estimated Phase 4 cost +5-8 s hosted.
- **D-46:** RUN-04: an important gate is one whose silent pass would let a requirement, claim or evidence tier be asserted without evidence (sole evidence, can pass vacuously, or its failure class escaped once). Mechanisms: fault (`faults/*.ids`, C behaviour in core/runner), control (scripts and verdicts), mutant (step-internal broken variants for the installed consumer). `data/expected/important-gates.ids` plus an `important-gates` step make coverage machine-checked; the Phase 4 list is in `04-DISCUSS-ci.md` §E table and planning finalizes it.
- **D-47:** Branch protection on `main` (PR required, 0 approvals, required check `gate`, no force-push or deletion) is RECOMMENDED here and recorded in AUTONOMY.md; applying it is a repository-settings action, so it is a documented owner/orchestrator-assist item (an agent cannot be assumed permitted); it blocks nothing in Phase 4. The release design (`release.yml` on `v*` tags, re-run the gate on the tag commit, `git archive` + install-tree tarball + SHA256SUMS, `gh release create`, allowlisted redistributable assets) is recorded and implemented later.

### Reconciliation (orchestrator, where research files disagreed)

- D6: logical input (controller agent) over electrical-per-channel (run-API agent); input event shape is the 32-byte `ivs_input_event` of D-13, replacing the run-API agent's 16-byte `{tick, channel, value}`.
- Digest composite: stays version 1 over domains 1..4 (run-API agent); domains 16..18 reported individually; the controller agent's "composite version bump" is withdrawn so Phase 3 literals stay.
- Guest observation names: `ivs_machine_cpu_state` and `ivs_machine_peek` (diagnostic agent) adopted for the run-API agent's `inspect/peek` proposal.
- Branch protection application is not an executor task.
