## 2.4 The checkpoint rule

At each phase boundary and at the close: recompute the last-five medians of
`cpu_s`, `build_s` and `gate_s` plus the token line from `.planning/ci-runs.tsv`
at the boundary commit; charge the phase's priced addition against 21; record
exactly one of `discharged-within-allowance`, `reprice` or `lever-required`.

`steps=38/38` is an invariant: any commit where it is not stops the milestone. A
phase overrunning its line by more than 25 percent is repriced before its next
plan. The priced unit is the **locally measured** addition (alternated before and
after, multiplied by 1.675 for the hosted scale), for the resolving-power reason
in 2.1.

## 2.6 What would blow the allowance

1. The discrimination cases registered as **faults** (4 x 0.44 = 1.76) instead
   of ids and controls — it also moves `faults=238`.
2. A **golden per trace or listing**: forbidden, 29 stays 29. A frozen artifact
   that a refactor merely re-blesses is not evidence.
3. A **per-id rebuild** or a preset-per-id launch: one cold build is about 34 s,
   roughly 1.6 times the milestone's whole price.
4. A **new gate step**: it re-opens the 38 invariant and the summary line for at
   most 0.1 cpu-s of content.
5. Separate stand-ins for all rival pairs (12 x 0.31 = 3.72 in one phase).

## 2.7 The durability rule

A trace or disassembly id survives a refactor only through four committed
bindings: (i) reconciliation with an existing report line (`step.*` or
`digest.*`), so it cannot pass on an empty or foreign trace; (ii) a liveness guard
asserting non-empty and cycle-monotonic output; (iii) a stand-in that makes that
guard **fail**, run in the same step rather than thrown away; (iv) a
project-authored guest with **both settings pinned**, so a default change
retargets every dependent expectation in one commit (the D-51/C41 precedent). No
golden carries the durability.

## 2.8 A new gate step is not needed

`tools/inspect/` follows `tools/flatwrap`: an `add_subdirectory` under the
existing presets, no install rule, `prefix-files` stays 11, so `c-build` already
builds it and its ids run inside existing suites.

**The exact evidence that reverses this:** a `c-build` log on the plan's own
start commit that does **not** contain the tool's build output while the tool is
present in the tree — that is, it needs a third configuration, or host-only
sources excluded from both presets. Only then is a step proposed, with that log
attached.
