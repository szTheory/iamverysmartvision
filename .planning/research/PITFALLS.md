# Pitfalls Research

**Domain:** Accurate, evidence-bound, deterministic headless Mattel Intellivision emulator (greenfield, owner-gated rights)
**Researched:** 2026-11-09
**Confidence:** MEDIUM overall. HIGH on process/rights-structure and on CP1610 interrupt/SDBD rules (primary-transcription plus two independent community docs agree). MEDIUM on STIC/PSG behavior (best sources are one expert's documentation plus community wiki; several numbers conflict). LOW on PAL, Intellivision II/Sears specifics, and EXEC/GROM legal ownership (no primary source reached).

## Critical Pitfalls

### Pitfall 1: Using another emulator (jzIntv, MAME, FreeIntv) as the oracle, or as the spec

**What goes wrong:** Expected values for CPU, STIC or PSG tests get generated by running jzIntv or MAME, or constants get copied from their sources. The new core then inherits every approximation and bug, and the test suite proves only "agrees with that emulator".

**Why it happens:** No permissively redistributable Intellivision conformance ROM suite was found (PROJECT.md evidence limit). Another emulator is the nearest executable reference, and its output looks authoritative.

**Concrete evidence that these emulators are not oracles:**
- MAME `stic.cpp` carries `// Collision Detection - TBD`, renders the whole frame in one pass (sprites and collisions per frame, not per scanline), does not check VBLANK on display-enable or mode writes even though its header says it should, and has an unexplained `- 1 - 1` on the right border. Its collision-register write stores the masked value instead of the hardware's described latch behavior. `[SRC S17]`
- MAME `cp1610.cpp` has `TBD` on HLT, TCI, SIN, EIS and DIS; says `Not supporting SDBD MVO@ or SDBD MVOI for now`; and marks SDBD with mode-110 operands `???`. `[SRC S18]`
- MAME `intv.cpp` marks vblank timing `/* not accurate */`. `[SRC S16]`
- jzIntv's own author marks the PAL numbers in his interrupt document as "very possibly BOGUS". `[SRC S8]`
- The STIC1A reverse-engineering notes list /BUSRQ timing, register-visibility duration, MOB visibility in v-delay rows and MOB-vs-border collision as unmeasured. `[SRC S15]`

**How to avoid:** `[REC]`
- Keep the evidence-tier vocabulary from PROJECT.md. "Independent implementation comparison" is its own tier, never a substitute for "source expectation" or "original diagnostic".
- Write expected values by hand from the GI manual / data sheets, with the page or section in a comment. Never generate a golden from this core or from jzIntv/MAME.
- A comparison against jzIntv/MAME is allowed only as a **disagreement finder**: every difference opens a labeled question (`[UNK]`), it is never auto-resolved in either direction.
- Treat every number from a community page as `[COMM]` until a second independent source or a measurement agrees.

**Warning signs:** Expected-value files with no hand-written derivation; a test named after an emulator rather than after a hardware rule; a fix that is "match jzIntv" without a data-sheet citation; REQUIREMENTS text that quotes a cycle count with no source tier.

**Phase to address:** A (policy), enforced in B, D, E.

### Pitfall 2: Same-core hash as a false oracle, and a title screen as false progress

**What goes wrong:** A framebuffer/audio hash is recorded from this core, then re-checked against itself. Two runs match, so the test is "green", while CPU flags, collision bits or PSG envelopes are wrong. Separately, "the EXEC title screen appears" is reported as compatibility progress.

**Why it happens:** Determinism is cheap to test and easy to mistake for correctness. The EXEC title screen exercises only a thin path: reset, the $1004 ISR, display-enable writes, BACKTAB and GROM cards, a few MOBs. It does not need sticky collisions, SDBD edge cases, PSG envelopes, controller multiplexing or non-NTSC timing. `[INF]` from the EXEC ISR listing in `[SRC S8]`.

**Consequences:** The roadmap marks "CPU done" or "STIC done" with no independent evidence; later accuracy work finds the "golden" files encode the bug and must all be regenerated.

**How to avoid:** `[REC]`
- Every golden file records its tier and its oracle in a header: `tier=original-diagnostic`, `expected-source=GI manual section X.Y` versus `tier=repeatability`, `source=this core, commit <sha>`. A repeatability golden may never be cited for an accuracy claim.
- Use **named-fault controls** (AGENTS.md): for each CPU/STIC/PSG/controller test, keep a mutated build or flag that breaks exactly the rule under test (for example: make interrupt checks happen after SDBD; clear collision bits on read; duplicate-byte rule removed) and require the test to fail. A test that cannot fail is not evidence.
- Guest-progress claims need a predicate on guest state (register/memory/marker), not a screenshot or hash. Title screen = `tier=boot smoke`, never "playable".
- A hash may only be compared across *different* implementations or *different* tiers, never core-vs-self.

**Warning signs:** Goldens committed in the same commit as the code change that produced them; a green suite with no failing negative control; progress reports that say "boots" or "shows title".

**Phase to address:** A (tier policy), F (fixtures and predicates).

### Pitfall 3: EXEC, GROM, MTE-201 and game ROMs: treating a hash as permission, and needing them in CI

**What goes wrong:** An EXEC/GROM image or MTE-201 cartridge ends up in the repo, in a CI cache, in a release artifact, or in a Docker layer because "its digest is in the manifest". Or CI cannot run anything without EXEC/GROM, so a private artifact is wired in and later leaks into logs or caches.

**Why it happens:** Intellivision software needs an EXEC image (reset at $1000, ISR at $1004) and a GROM (font/graphics cards). jzIntv itself does not ship them. `[SRC S19]` `[SRC S11]` Its repo `rom/` directory contains only `.gitkeep`. `[SRC S19]` Its README points users at Intellivision Lives! / Rocks! CDs for EXEC.BIN, GROM.BIN and game ROMs, and states that Intellivision is a trademark of Intellivision Productions and that jzIntv is unaffiliated. `[SRC S19]` `[SRC S20]`

**Rights state (as of 2026-11-09):**
- Who holds copyright in EXEC/GROM/MTE-201 today is `[UNK]`. A forum claim says the EXEC/GROM were left out of public distribution to avoid infringing Intellivision Productions' copyrights; this is a forum opinion, not a legal source. `[COMM S20-search]`
- Ownership chain reported by community sources: Intellivision Productions was renamed Blue Sky Rangers Inc. and its video-game IP was transferred to Intellivision Entertainment, which sold the brand and "certain games" to Atari in May 2024. `[COMM S23]` `[SRC S22]` Whether EXEC, GROM, manuals, overlays or the MTE-201 cartridge were part of any transfer is not stated by any source I reached. `[UNK]`
- The 2609 service manual scan is hosted by a third party; reuse rights are unreviewed. `[SRC EMULATOR-DNA]`

**How to avoid:** `[REC]`
- Fixture manifest fields (already required by PROJECT.md): source, recipe, digest, license, notices, allowed use, **and a separate `redistributable: yes/no/unknown` column**. Digest column answers "which bytes", the redistributable column answers "may we ship". `unknown` is treated as `no`.
- The default CI profile uses only **project-authored** fixtures built from source in CI (assembled in the job, not committed as binaries). EXEC/GROM-dependent tests are a separate, clearly named, optional job that skips with a visible `SKIPPED: no user-supplied system image` line, and the skip is counted in the report (see Pitfall 16).
- Never put system images in CI caches, artifacts or container layers. If an owner-approved private path is ever created, it is a mounted read-only secret, with log redaction and an artifact denylist test.
- Do **not** write an original EXEC replacement casually: it must reproduce the contract guests rely on (reset at $1000; ISR dispatch at $1004 calling the vector stored at $0100/$0101 in double-byte form; a NOP at $1009 so BUSRQ can be serviced) `[SRC S8]`, and its presence changes timing. Any evidence gathered with it is bound to profile "project EXEC", not to "2609 + real EXEC" (Pitfall 15).

**Warning signs:** A `*.bin`/`*.int`/`*.rom` anywhere in the tree or in a cache key; a test that fails on a clean checkout without a hidden file; a manifest with a digest and no rights column; MTE-201 files referenced by path.

**Phase to address:** A (rights policy and manifest schema), C (system-image refusal), F (CI shape). **Owner gate** for any actual third-party content.

### Pitfall 4: GPL contamination and clean-room provenance (jzIntv, MAME)

**What goes wrong:** Code, tables, timing constants or comments get ported from jzIntv, or from MAME files believed to be "BSD so safe". The project then cannot choose a permissive license, or inherits obligations unknowingly.

**Facts:**
- jzIntv's repo carries GPLv2 text, and the README says "GPL v2 or later". `[SRC S19]` The upstream author site was unreachable during this research (connection refused), so the license of the *upstream* tree, as opposed to the FujiNet fork, was not re-verified. `[UNK]`
- jzIntv's source contains purpose-built timing data (for example a `stic_timings.h` included by `stic.c`) `[SRC S19]` that is precisely the kind of table that is tempting to copy.
- MAME licensing is per file: `intv.cpp`, `stic.cpp` and `cp1610.cpp` all read `// license:BSD-3-Clause`. `[SRC S16][SRC S17][SRC S18]` But `cp1610.cpp`'s own header says "Special thanks to Joe Zbiciak for his GPL'd CP1610 emulator" and says the work is based on a different emulator plus the data sheets. `[SRC S18]` Whether that is derivative of GPL code is a legal question this research cannot answer. `[UNK]` A per-file BSD tag is therefore not proof that a file is clean for copying.
- jzIntv's `doc/` tree includes a transcription of the GI CP-1600 manual (`cp1600.txt`, with OCR damage such as "ceunter"). `[SRC S12]` The transcription's copyright status is `[UNK]`, and it has OCR errors, so it is a reading aid, not a citable primary source.
- IntyBASIC: the compiler is under a BSD-2-clause license ("Source code license"). `[SRC S21]` See Pitfall 5 for the output.

**How to avoid:** `[REC]`
- Written provenance rule: *read for understanding is allowed; copy, transliterate, or port is not, without an owner-approved license decision.* Record, per module, "implemented from: <GI manual section / data sheet / measurement>", never "from jzIntv".
- Do not paste jzIntv/MAME tables, struct layouts, constants or distinctive comments. Re-derive numbers from the primary source and note the derivation.
- Keep a third-party-notices file from day one, even if empty, so a later copy is a visible event.
- Dependencies: reject any GPL dependency for the core (the Core Value and AGENTS.md prefer a small tree; license choice is an owner gate).
- Process: if one person reads GPL source for debugging help, record it; the implementer of the corresponding module should be someone who derived it from the data sheet. `[REC]` (a clean-room discipline; whether it is legally required here is for the owner to decide.)

**Warning signs:** A constant with a suspiciously specific value and no derivation; code comments that echo another emulator's wording; commit messages "port from jzintv"; any `#include` or build rule pulling in jzIntv/MAME files.

**Phase to address:** A (policy), every implementation phase (review checklist).

### Pitfall 5: Trademark, brand ownership, naming, and homebrew/IntyBASIC license ambiguity

**What goes wrong:** The project name, documentation, release artifacts or sample content imply affiliation with, or rights from, whoever owns Intellivision; or a homebrew ROM or IntyBASIC-compiled fixture is committed as "free" when it is not licensed for redistribution.

**Brand ownership (verify before any public use):**
- Atari announced on 2024-05-23 that it acquired the Intellivision brand and rights to about 200 games from Intellivision Entertainment LLC; the Amico console and the company stayed behind, rebranded. `[SRC S22]` Several outlets report the trademarks went with the brand; a forum post citing USPTO records lists assignments executed 2024-05-20 and recorded 2024-06-03 to Atari Interactive, Inc. (secondary; verify on USPTO). `[COMM S22-search]`
- Atari/Plaion announced the Intellivision Sprint in October 2025 with US shipping from 2025-12-05 (several press reports). `[SRC S24]` So a live commercial product exists under the mark; the risk of a confusingly similar name or "Intellivision-compatible" claims is higher than for a dormant brand.
- A single community site says Intellivision Entertainment became "Happy Home Games" and that Atari also bought the AtariAge forum. `[COMM S23]` Not verified by a second source; do not rely on it.
- "Mattel" is a separate mark from "Intellivision"; this research did not find who may use it descriptively. `[UNK]`
- Atari acquired a *brand and selected game library*. No source I reached says it acquired EXEC/GROM/manual copyrights or granted emulation permission. Atari ownership therefore is **not** a permission path. `[INF]`
- `iamverysmartvision` is an owner-chosen working name and "not trademark-cleared" (PROJECT.md). It does not contain the word "Intellivision", but it is used next to it.

**Homebrew and IntyBASIC:**
- Homebrew ROMs have no uniform license. An AtariAge admin statement (2003) is that ROMs hosted there are "legal" because the authors authorized distribution there; that is a hosting policy, not a general license, and is a forum quote. `[COMM S28]`
- IntyBASIC's `LICENSE` is BSD-2-clause for the **compiler**; its own README labels it "Source code license" and does not say what applies to compiled programs. `[SRC S21]` Compiled programs embed `intybasic_prologue.asm` and `intybasic_epilogue.asm`. `[SRC S21]` Their headers (first ~25 lines read) carry only revision history; they credit contributed routines by James Pujals, "intvnut" suggestions, Joseph Zbiciak's number-printing and Intellivoice routines, with no per-file license text. `[SRC S21]` The manual shows the assembler can embed `ASM CFGVAR "license" = "public domain"` in the build metadata, i.e. the *author* declares output license. `[SRC S21]` Whether embedded runtime code imposes obligations on a compiled ROM is `[UNK]`.

**How to avoid:** `[REC]`
- Treat naming, domain, repo visibility and any "Intellivision" in a product name or package id as an **owner gate** with a trademark check before external publication. Use descriptive, factual wording ("emulator for the Mattel Intellivision family") only in docs, and never in a program/package name or logo without clearance.
- Every homebrew/IntyBASIC fixture needs: author, license statement *from the author*, the compiler and library versions, and the recorded notice text for the runtime. If the author gave none, it is `redistributable: unknown` and stays out of the repo.
- Prefer project-authored assembly fixtures (as1600-compatible or own assembler) over IntyBASIC output for committed fixtures, so runtime-library provenance never enters the picture.
- Do not use screenshots, box art, overlay images, "Running Man" logo or manual text in docs/README.

**Warning signs:** The README or package metadata containing "Intellivision" as a product name; homebrew `.bin` committed because "it's on AtariAge"; a fixture manifest with `license: free`.

**Phase to address:** A (policy and naming gate), F (fixture rights). **Owner gate.**

### Pitfall 6: CP1610 interrupt model: instruction-granular checks, SDBD, EIS/DIS, and BUSRQ

**What goes wrong:** The emulator tests for interrupts after every instruction, or ignores the "previous instruction was interruptible" condition, or treats BUSRQ as maskable. Results: the ISR fires a different instruction later than hardware, STIC bus requests are serviced at wrong times, the display shifts down one row, 16-bit vector hooks tear.

**What the sources say:**
- Rule: INTRM is checked only if the I flag is set **and** the previous instruction was interruptible; BUSRQ is checked after interruptible instructions **regardless** of the I flag. `[COMM S2]` Consistent with the jzIntv interrupt doc, which tells programmers to hook the ISR vector with MVO@/SWAP precisely because those are non-interruptible. `[SRC S8]`
- Non-interruptible set per the wiki: HLT, SDBD, EIS, DIS, TCI, CLRC, SETC, the shifts/rotates (SWAP, SLL, RLC, SLLC, SLR, SAR, RRC, SARC), and all MVO forms. `[COMM S2]` The GI summary table agrees for HLT/SDBD/EIS/DIS/TCI/CLRC/SETC. `[SRC S13]` Shifts and MVO should be verified against the GI manual instruction pages, not only the wiki. `[REC]`
- jzIntv's own debugger exposes an "i" flag meaning previous instruction was interruptible and a "D" flag. `[COMM S2-search]` That implies the state must be explicit in the core, not derived.
- MAME handles SDBD-prefixed instructions as uninterruptible by construction instead of tracking a mask bit. `[SRC S18]` That is a shortcut that can hide differences when an interrupt or BUSRQ lands between SDBD and its operand instruction.
- EIS/DIS are non-interruptible, so by the rule above the instruction after EIS runs before an interrupt can be taken. `[INF]` Verify with a vector test; the wiki does not discuss it directly.
- STIC timing consequence: the STIC asserts BUSRQ for 114 CPU cycles on NTSC and the CPU "must halt within about 57 cycles" or the display duplicates the previous row and shifts down. `[COMM S2]` The jzIntv doc advises at most about 3-4 MVOs or 4-5 shifts in a row (~30-40 cycles). `[SRC S8]` The exact bound is `[UNK]` (see Pitfall 7).
- `[SRC S8]` The EXEC dispatcher at $1009 has an explicit interruptible NOP "needed for STIC": the real EXEC is written around this rule.

**How to avoid:** `[REC]`
- Model `prev_interruptible`, `I`, `D`, and a pending-bus-request line as explicit CPU state. Check INTRM/BUSRQ at one named point (end of each instruction), with a table of per-opcode interruptibility sourced from the GI manual.
- Hand-written vector tests: (a) interrupt pending + EIS → exactly one more instruction runs; (b) interrupt pending during SDBD → ISR return address is after the operand instruction, not between; (c) BUSRQ pending with I=0 still halts after an interruptible instruction; (d) a run of N non-interruptible MVOs delays the halt by N instructions.
- Named-fault controls for each of (a)-(d).

**Warning signs:** One boolean "interrupts_enabled" and no "previous instruction" state; interrupt tests that only use NOP-padded sequences; the first display glitch being "the screen scrolls down a row" in long MVO sequences.

**Phase to address:** B (CPU rules), D (BUSRQ coupling).

### Pitfall 7: STIC timing windows and "a frame is N cycles"

**What goes wrong:** A frame is hard-coded to one cycle count; the register-access window is a single constant; PAL is "NTSC with other numbers". Guest code that depends on window length (long ISR, late STIC writes) behaves differently than hardware.

**Conflicting numbers (do not freeze any without a measurement):**
| Quantity | Source A | Source B | Status |
|----------|----------|----------|--------|
| STIC register visibility after VBlank interrupt (NTSC) | ~2900 cycles, display active `[COMM S4]` | ~2000 cycles `[SRC S8][SRC S11]` | `[UNK]` conflict |
| GROM/GRAM visibility | "VBlank Period 2" shorter/longer than regs, no number `[COMM S4]` | ~3780 cycles (Bus Copy 3780-3790) `[SRC S8]` | `[UNK]` |
| CPU cycles per NTSC frame | display disabled 14,934; display enabled with vertical delay 0 about 13,518; with vertical delay > 0 about 13,572 `[SRC S8]` | - | single source, author-measured |
| BUSRQ-to-BUSAK delay, exact cycles | page gives scanline-level only `[COMM S3]` | /BUSRQ "~1 CPU cycle shorter" in jzIntv experiments `[SRC S15]` | `[UNK]` |
| PAL: frame/scanline/cycles | "no data" `[COMM S4]` | ~20,000, 312 lines, 8,840-8,850, marked "?? ... BOGUS" `[SRC S8]` | `[UNK]` |

**Derived facts to bake in carefully:** `[INF]` from `[SRC S8]`: NTSC CPU clock = 3,579,545 / 4 = 894,886.25 Hz; 894,886.25 / 14,934 = 59.92 Hz (not 60 and not 59.94). Any audio resampling or frame pacing built on 60 or 59.94 drifts.

**The frame is not a fixed cycle count:** the number of CPU cycles available per frame depends on whether the display is enabled and on vertical delay, because the STIC steals bus time. `[SRC S8]` So "run one frame" and "run N cycles" are different bounds (Pitfall 17).

**How to avoid:** `[REC]`
- Put every timing number in a **profile data file** with a per-field tier (`source-expectation`, `measured`, `unknown-default-chosen`), not as scattered constants.
- Where sources conflict, implement the more conservative documented value as a **named policy**, tag it `unknown-default-chosen`, and write a diagnostic fixture whose expected outcome is "documented and may change".
- PAL is `[UNK]`; do not claim it in profile 1 (PROJECT.md already defers it).
- Do not design time units that assume integer cycles per audio sample or per frame.

**Warning signs:** `#define CYCLES_PER_FRAME`; 60 or 59.94 anywhere; a timing test that passes only for NTSC; a second source quoted without noting the conflict.

**Phase to address:** A (profile data), D (STIC), F (runner bound semantics).

### Pitfall 8: STIC register/GRAM visibility semantics and read side effects

**What goes wrong:** The emulator lets the CPU read/write STIC registers, GRAM and GROM at any time; or treats reads as pure. Games that rely on writes being dropped or reads being unreliable behave differently, and, worse, a debugger/"peek" API silently changes machine state.

**Facts:**
- During active display the STIC owns GROM, GRAM and its registers: writes are dropped and reads return garbage. `[SRC S8]` The memory map distinguishes "VBLANK 1" (~2000 cycles), "VBLANK 1a" (CPU cannot see the value read), "VBLANK 2" (~3780) and "2a". `[SRC S11]`
- Display must be re-enabled every frame by a write to $0020; otherwise the display blanks while VBlank interrupts continue. `[SRC S8]`
- STIC registers appear to lose their state if interrupts are not taken for a few frames. `[SRC S8]` ("appears": an observation, not a measured fact.)
- **Reads have side effects:** reading $0021 (or its aliases $4021, $8021, $C021) during VBlank Period 1 switches the STIC into Color Stack mode; writing it selects FGBG. `[COMM S4][COMM S7]` MAME's source also says any read during VBLANK enables color stack/colored squares. `[SRC S17]`
- The STIC decodes $0000-$007F in System RAM glue but responds only to $00-$3F; aliases at $4000/$8000/$C000 are reported. `[COMM S7]` `[COMM S4]` GRAM has shadow copies at $3B00-$3FFF (incomplete address decode). `[SRC S11]`
- If the CPU ignores BUSRQ for long enough, System RAM stays in Bus Copy mode and "bus fights" can occur. `[COMM S3]` The real behavior of these states is not defined by the sources. `[UNK]`

**How to avoid:** `[REC]`
- "Garbage" and "bus fight" are **undefined hardware behavior**; a deterministic core must choose a documented policy (for example: reads return a fixed pattern, writes dropped), name it in the profile, and never leak host randomness or uninitialized memory.
- Separate `peek` (no side effects, for debuggers/tests) from `read` (CPU bus read). Test: `peek($0021)` leaves mode unchanged; `read($0021)` in window switches mode; `read($0021)` outside window does not.
- Test out-of-window access explicitly (write dropped; read policy value) and aliases.
- Model the display-enable handshake as state.

**Warning signs:** Debugger or state-dump code calling the same function as the CPU bus; STIC tests that never touch active display; "mode" implemented as a plain register write.

**Phase to address:** D.

### Pitfall 9: Per-frame rendering where hardware works per row/scanline

**What goes wrong:** The frame is rendered in one pass from end-of-frame register state (this is exactly what MAME's `stic.cpp` does `[SRC S17]`). Effects that depend on *when* something changes within the frame are lost: BACKTAB edits made during active display, color-stack advances, a late BUSRQ shifting rows.

**Why it matters here:** BACKTAB lives in 16-bit System RAM. At each card-row fetch the STIC reads 20 cards via BUSRQ/BUSAK into a 20-entry FIFO in System RAM and then the RAM *replays the same 20 cards for the next 15 scanlines*; new cards are not loaded without another BUSAK. `[COMM S3]` From this, the effective granularity of BACKTAB is a row fetch, not a frame, and if the CPU does not acknowledge in time the previous row repeats and everything shifts down one row. `[INF]` from `[COMM S3]` and `[COMM S2]`.

**How to avoid:** `[REC]` Make the raw framebuffer observable at a defined **machine-time boundary** (PROJECT.md requirement) and decide the rendering granularity up front: either row-granular (fetch at BUSAK time) or documented as "frame-granular approximation, accuracy claim limited accordingly". An approximation is legitimate only when it is named in the profile and a test shows what it cannot represent.

**Warning signs:** A single `render_frame()` reading registers at vblank; no concept of the 20-card FIFO or of "rows fetched so far".

**Phase to address:** D (decide early; retrofitting is a rewrite).

### Pitfall 10: Visible geometry, border, delay, and what "raw framebuffer" means

**What goes wrong:** The raw framebuffer is 160x96 because 20 cards x 8 px = 160, or 192 lines because the NTSC active scanline count is 192, or the border/overscan is cropped without recording it. Goldens then disagree with every other implementation, and hosts cannot scale correctly.

**Facts and conflicts:**
- Visible background is 20x12 cards but **159x96 pixels**; the rightmost column is not displayed. `[SRC S10]` `[COMM S7]` The object field is 167x105 (NTSC) or 168x104 (PAL) and starts 8 px above/left by default. `[SRC S10]` MAME has an unexplained `- 1 - 1` on the right border and `-1` in draw_borders, i.e. the same off-by-one confusion. `[SRC S17]`
- 192 active scanlines vs 96 pixel rows: scanline-level and pixel-level resolution differ. `[SRC S8]` What the raw framebuffer's vertical size should be is `[UNK]` and is an owner/profile decision.
- Horizontal and vertical delay (3-bit values, scroll), border extension bits (bit 0 left, bit 1 top) and the border color registers interact: delay > 0 exposes the otherwise blank top/left object-field area unless blocked. `[SRC S10]` Whether MOBs are visible in rows exposed by v-delay > 0 is unmeasured. `[SRC S15]`
- The STIC1A (variant) displays a 160th column unlike the AY-3-8900-1, with possible MOB-vs-border collision effects. `[SRC S15]` Which console revisions use which STIC part is `[UNK]`.

**How to avoid:** `[REC]`
- Define "raw video" in the profile: dimensions, origin, which pixels are border, bits per pixel/palette-index vs RGB, and whether the delay-exposed area is included. Emit **palette indices + a separately specified palette**, since the NTSC color rendering (RGB values) is a host presentation choice. Store the crop in the golden header.
- Diagnostic fixtures for each geometry rule (edge cards, delay values 0/7, border-extension bits, MOB at x=0, y=0).

**Warning signs:** Magic numbers 160, 192, 240 in the framebuffer path; goldens that are RGB PNGs; "off by one on the right edge" bugs that get fixed by editing the golden.

**Phase to address:** A (define raw boundary), D.

### Pitfall 11: MOB, collision, FGBG and Color Stack semantics

**What goes wrong:** Collision bits are cleared on read or overwritten on write; self-collision appears; hidden MOBs do not collide; Color Stack/FGBG card-index and color limits are not enforced; foreground priority is applied wrongly.

**Facts:** `[SRC S10]` unless noted
- Collision bits are **sticky** until the CPU clears them; the CPU can also set them by writing the collision register; bit N of MOB N never reads 1; writing MOB Y's bit X does not change MOB X's bit Y.
- A MOB does not need to be visible to interact with other MOBs, cards or border. MOBs interact with border (COLL BORD), background (COLL BG) and other MOBs.
- In Colored Squares, colors 0-6 are treated as "set" (interact) and 7 as clear; color 7 uses the top stack color and does not advance the stack. `[COMM S7]`
- FGBG mode: GROM cards limited to 0-63 and attribute bits 9/10 ignored (only 128 of 320 pictures available), pastel colors 8-15 unavailable as foreground. `[SRC S10]` `[COMM S7]`
- Color Stack: pointer advances on an ADV bit and wraps after $2B; GRAM cards can use the full 16-color palette and get extra flag bits. `[COMM S7]` On the STIC1A, "does not appear to provide a mechanism to disable the additional GRAM"; games that don't zero bits 10:9 display incorrectly. `[SRC S15]`
- MAME: stores the masked value on write instead of latch-style behavior, sets sprite-behind-foreground collisions per its header note, collisions computed per frame. `[SRC S17]`
- Bit 3 of $0022 reads 0 and has no known function. `[SRC S15]`

**How to avoid:** `[REC]` Vectors per rule: read-twice persistence; CPU set/clear; self-bit; invisible-MOB collision; each colored-squares color; FGBG card limit; stack wrap. Do not take "sprite behind foreground" collision semantics from MAME; mark `[UNK]` until a data sheet or measurement settles it.

**Warning signs:** Collision implemented as a pure function of the final pixels; a single "collision register" without per-bit rules; a test with two MOBs only.

**Phase to address:** D.

### Pitfall 12: PSG (AY-3-8914): wrong chip, wrong register order, wrong envelope, wrong output cadence

**What goes wrong:** An AY-3-8910 library or data sheet gets used as-is. Registers are in the wrong order, the 8914's 2-bit envelope-select is collapsed to 1 bit, envelopes use a different step count, volumes use the wrong DAC curve, and raw audio is entangled with the host sample rate.

**Facts:**
- The Intellivision part is an AY-3-8914 (same pinout as 8910; the register layout is shuffled). `[COMM]` (MAME comments and jzIntv doc; the part's A7-A4 enable state is mask-programmable and was 0000 for the Intellivision part. `[COMM S2-search ay8910.cpp]`)
- Master Component register map at $01F0-$01FF: periods A/B/C low, envelope period low, periods high, enable, noise period, envelope type, volumes A/B/C, then $01FE/$01FF controller inputs (right/left). The mapping to 8912 data-sheet register numbers is *not* sequential (R0, R2, R4, R13, R1, R3, R5, R14, R7, R6, R15, R10-R12). `[SRC S9]`
- Volume registers have **two envelope-select bits** (bits 5:4: 00 fixed; 01 envelope >> 2; 10 envelope >> 1; 11 envelope directly) on the 8914; later units' and the ECS's AY-3-8916/8917 implement **one** bit like the 8912. `[SRC S9]` The STIC1A notes say bits 5:4 "behave unusually for values 01b and 10b" and call the part "mostly an AY-3-8914 clone" with zero evidence of an AY8930 clone. `[SRC S15]` So PSG behavior differs by console revision; profile naming matters (Pitfall 15).
- Clock: PSG clocked at half the master clock (3.579545 MHz NTSC / 4.0 MHz PAL); tone F = master / (32 x P); full envelope cycle F = master / (512 x P_env); one envelope step = one tone period for the same period value. `[SRC S9]`
- Tone period 0: the wiki (as summarized by a fetch tool) says 0 acts as 4096 and envelope period 0 as $20000. `[COMM S6]` Many AY emulators treat tone period 0 as 1. `[INF]` from general emulator practice, not from a source I read. **Conflict, `[UNK]` for the 8914.**
- Envelope: the AY-3-8910 envelope counter has 16 steps; the YM2149 has 32 steps at twice the speed, and at least one emulator documentation says it deliberately uses YM2149 behavior for everything. `[COMM S27]` Using a library built that way gives a smoother curve that is not the 8914's.
- Noise: the wiki describes a shift-and-XOR feedback with the lowest bit as source and does not give width or taps. `[COMM S6]` LFSR width/taps and reset value are `[UNK]` here; they are the classic source of "noise sounds different" bugs and affect hash-level audio comparisons.
- Volume DAC: logarithmic steps, 0 to 1 V normalized. `[SRC S9]` Exact per-level amplitudes are `[UNK]`; the STIC1A notes list audio output polarities as "not known definitively yet". `[SRC S15]`
- Controller I/O ports are PSG ports; R7's top bits set port direction and should normally be 0 on the Intellivision except when scanning ECS keyboards. `[SRC S9]`

**How to avoid:** `[REC]`
- Do not adopt a generic AY library without checking each of: register order, two-bit envelope select, period-0 rule, envelope step count, noise LFSR, DAC table.
- Make the core's audio output **register-write events with machine timestamps plus raw chip-rate samples** (nominal 3.579545 MHz / 16 = 223,721.5625 Hz on NTSC per `[COMM S6]`; derive from the divider, don't trust the number). Host resampling/PCM conversion is a separate step and must not be in the evidence path for chip behavior.
- Specify numeric type of the audio path (integer or fixed-point) so hashes are portable; floating-point mixers produce platform-dependent hashes.
- Test vectors per rule (tone period boundaries, each envelope shape, both envelope-select bits, noise sequence for N steps), derived from the GI documentation, not from the core.

**Warning signs:** Register names from the 8910 data sheet in the code; 44.1 kHz constants inside the PSG; a single "envelope" bit; audio goldens that differ between macOS and Linux.

**Phase to address:** E.

### Pitfall 13: Hand controllers modeled as joystick + buttons

**What goes wrong:** Controllers become "dpad + buttons" with independent bits. The 12-key keypad, 16-direction disc and three side buttons share an 8-bit active-low port; some combinations cannot be decoded uniquely, so a host that sends "any combination" produces states real hardware cannot. Two-controller reads are not multiplexed as on hardware.

**Facts:**
- Active-low: pressing clears bits; no key reads all 1s in the low 8 bits (key 1 reads $7E; keys 1+9 read $5A). `[COMM S5]`
- Keypad alone decodes uniquely; side button + disc decodes; keypad with side button or disc cannot be uniquely decoded; two side buttons together cannot. `[COMM S5]`
- Right controller at $01FE, left at $01FF (PSG I/O ports); sample code ANDs the two values because active-low merges with AND. `[SRC S11][COMM S5]`
- The page does not describe the disc's 16-direction encoding or the keypad matrix. `[COMM S5]` So the electrical model is `[UNK]` until sourced from schematics, software or measurement (EMULATOR-DNA already says this).
- jzIntv's pad module keeps per-controller arrays of 18 event inputs "for the event subsystem" and a `stale` flag. `[SRC S19]` That is host-event coupling inside the device model; do not copy the shape.
- Ports are shared with the ECS keyboard (when the ports are driven as outputs) and the Intellivoice expansion bus overlaps $01FE-$01FF. `[SRC S9][SRC S11]`

**How to avoid:** `[REC]`
- Core input = **electrical state per port** (two 8-bit values, or their sources) plus the direction register effect; the host-facing "logical" layer (keys, disc angle, side buttons) is a separate, replaceable mapping that *produces* a physically realizable electrical state. Document what the core does when the host requests an unrealizable combination (refuse, or apply AND-merge; choose and test).
- Arithmetic note `[INF]`: two ports x 8 bits fit a 32-bit mask with room; a one-hot logical encoding (12 keys + 16 directions + 3 buttons per controller, two controllers = 62 bits) does not. That matters for the LibFuturo candidate (32-bit mask sampled at advance start `[SRC PROJECT.md]`): fit is unconfirmed, and the electrical encoding may be the one that fits.
- Tests (after sourcing): each key, each disc direction, each side button, both players, and a named list of ambiguous combinations with expected AND-merged result.

**Warning signs:** `uint8_t buttons` + `uint8_t dpad`; no test where both controllers are pressed; "disc" stored as an angle in the core.

**Phase to address:** E (after A decides electrical vs logical).

### Pitfall 14: Cartridge/ROM images, 10-bit ROM, memory widths and silent defaults

**What goes wrong:** ROM data is treated as 16-bit words; ROM images in different formats are mis-parsed (endianness, header, CRC, segments); an unknown memory map is silently replaced with a default; 8-bit RAM and 16-bit RAM widths are conflated; malformed content crashes instead of being refused.

**Facts:**
- Instructions are 10-bit "decles"; addresses and registers are 16-bit. `[COMM S1]`
- Different widths in one address space: 8-bit scratch RAM $0100-$01EF, 16-bit system RAM $0200-$035F, GROM $3000-$37FF, GRAM $3800-$3AFF with shadow copies to $3FFF, Intellivision II EXEC extension at $0400-$04FF, Intellivoice expansion bus, Intellicart bank-switch registers at $0040-$005F (write-only), ECS ROM banks starting at $2000. `[SRC S11]` Read-back of the unused upper bits on narrow memories is `[UNK]` in these sources.
- Image formats: `.bin`/`.int`/`.itv` + `.cfg` (jzIntv assumes BIN+CFG and falls back to a standard Mattel map when no cfg exists); `.rom` (Intellicart) has a 0xA8 marker, a segment count and its complement; the plain ROM format cannot express ECS/Mattel bank switching. `[COMM S26]`
- Doc says the BIN+CFG source is "close to a spec" (jzIntv's `bincfg`). `[COMM S26]` That is a GPL source; do not use it as the format spec (Pitfall 4).
- jzIntv has a fall-back default map. `[COMM S26]` A silent default can mask a wrong cartridge map.

**How to avoid:** `[REC]`
- First profile accepts exactly one documented image layout (decle storage, endianness, address placement) defined in the project's own words; unsupported formats and unknown maps are **refused with a specific error**, never guessed.
- Refusal tests (PROJECT.md requirement): empty, odd length, truncated segment, overlapping segments, segment crossing a memory-class boundary, ROM claiming I/O or STIC ranges, bank-switch writes in a profile that has none, oversized content, wrong header tag.
- Model decles explicitly (a 10-bit type or masking policy) and test that high bits are stripped or refused on load, and that stores to 8-bit memories truncate as documented.

**Warning signs:** `uint16_t rom[]` with no mask; a loader that "just tries" a map; a content hash used as the only compatibility key.

**Phase to address:** C.

### Pitfall 15: EXEC startup, power-on state, and Intellivision II / Sears / variants

**What goes wrong:** Boot tests pass with a minimal EXEC and fail with the real one (or vice versa); power-on RAM contents are random or zero in a way that changes guest behavior; the profile name hides which EXEC/PSG/STIC revision was modeled; Intellivision II behaviors (lockout, timing) are claimed accidentally.

**Facts:**
- Reset starts at $1000; the interrupt vector is $1004 in the EXEC. `[COMM S1]` `[SRC S11]` After reset, the STIC generates a reset-related signal for at least 10 ms (reset line pulse). `[SRC S14]`
- Real programs rely on power-on RAM garbage: the IntyBASIC prologue revision note says it seeds the random generator "using trash in 16-bit RAM", and uses PAL/NTSC detection code. `[SRC S21]` A deterministic core must therefore define power-on RAM contents as a **profile parameter** and the runner must record it; guest behavior depending on RNG seed is otherwise undefined.
- Intellivision II: community reports its EXEC was modified to block unlicensed titles via a cartridge-header bit, and that the modified EXEC introduced a slight timing error with minor sound-effect problems. `[COMM S25]` Forum claims; no technical documentation was reached. There is also a II-specific EXEC extension region at $0400-$04FF. `[SRC S11]` The Intellivision II also changed the external video circuit. `[SRC S14]`
- Later PSG chips (8916/8917) differ in envelope-select bits (Pitfall 12). `[SRC S9]`
- Sears Super Video Arcade and Intellivision II are listed in MAME's configuration families. `[SRC EMULATOR-DNA]` Existence in another emulator does not imply support (PROJECT.md).

**How to avoid:** `[REC]`
- Profile identity = (console model/revision, STIC part, PSG part, EXEC identity as digest, GROM identity as digest, region/timing, power-on RAM policy, cartridge arrangement). Every claim, golden and report is tagged with it. A different EXEC digest is a different profile.
- Keep a hand-written boot-contract test (reset vector, ISR dispatch, ISR vector hook via double-byte write) that runs against whichever EXEC is configured, so an EXEC replacement is checked against the contract, not against a golden.
- Keep GROM out of the visual oracle: write diagnostic fixtures that draw only from **GRAM cards they define** so framebuffer goldens do not depend on GROM glyph bytes (which are rights-bearing and revision-specific).
- Explicitly list II, Sears, ECS, IntelliVoice, PAL as out-of-profile; refuse or label "unsupported profile".

**Warning signs:** Goldens that include BIOS text rendering; "works on Intellivision" without a profile id; a RAM init of "whatever malloc gave".

**Phase to address:** A (profile identity), C (system-image identity), F.

### Pitfall 16: Stale goldens, skipped-but-green tests, and CI caches masking stale output

**What goes wrong:** A required test silently does not run (fixture missing, filter matched zero, runner exits 0 on an empty set) and CI reports green; a cached build or cached output artifact is reused after the code or fixture changed; golden files are regenerated by the same change that broke them.

**Domain-specific forms:** `[INF]`
- EXEC/GROM-dependent tests "skipping" when the private image is absent is the *default* in a rights-restricted project, so skip-as-green is the path of least resistance.
- Fixture-from-source builds (assembling a diagnostic) can fail soft and leave a previous `.bin` in a cache or build dir.
- Golden hashes updated with `--update` flags.

**How to avoid:** `[REC]` (consistent with AGENTS.md and EMULATOR-DNA)
- **Exact test inventory file** checked in; the gate compares executed IDs to inventory and fails on missing, duplicated, or extra tests. Report counts: `executed / skipped / missing / expired`.
- Distinguish in output: harness failure, guest failure, timeout, cancellation, missing fixture (EMULATOR-DNA). Missing required fixture = failure, not skip. Optional-tier skips print a reason and are counted in the summary line.
- Bind cache keys to *content digests* of source, fixtures, toolchain and profile; add a stale-output check: every golden/artifact records the producing commit and fixture digest, and the gate fails if inputs changed but the output did not. Run one CI job with the cache cleared as a periodic control (PROJECT.md: "measure before changing caches").
- Goldens are updated only through a script that prints the diff and requires a tier annotation; a PR check forbids changing a golden and its producing code in the same commit without a reviewer note. `[REC]`
- Named-fault controls (Pitfall 2) catch tests that cannot fail.

**Warning signs:** CI time suspiciously low; "0 tests" in a log; `|| true`; goldens changing in diffs without code changes in the matching module; cache restore hits when fixtures changed.

**Phase to address:** F (CI shape); policy in A.

### Pitfall 17: API/integration: wall clock, host input, bounds, buffers, global state

**What goes wrong:** The core leaks host time or host input; "run a frame" has ambiguous meaning; output buffer lengths vary; instances share mutable globals; saves break silently.

**Domain-specific forms:**
- **Wall-clock leakage:** jzIntv's STIC module includes a speed/throttle module, a GIF encoder, a graphics module and file I/O in `stic.c`, i.e. pacing, presentation and file access are coupled to the device model. `[SRC S19]` Do not model that shape. The only time in the core is machine time (CPU cycles or a derived unit).
- **Host-input polling inside the core:** see the pad module's event arrays (Pitfall 13). Input is **supplied** to an advance call at a named machine-time boundary and sampled by the device model when the guest reads, with the boundary rule documented (sampled at advance start vs at read time changes what a guest sees).
- **Frame-vs-cycle bound:** cycles per frame vary with display enable/vertical delay (Pitfall 7). Offer *cycle-bounded* execution as primary, with frame-bounded defined as "to the next vblank interrupt boundary" in terms of machine time; report actual cycles consumed.
- **Buffer ownership:** the number of audio samples per frame is not an integer for a naive rate (894,886.25 Hz / 14,934 cycles). `[INF]` Output sizes must be variable and reported; caller-owned buffers need a "capacity too small" refusal that leaves state unchanged (EMULATOR-DNA). The raw video boundary needs a defined stride/pixel format.
- **Instance global state:** `[REC]` ban mutable statics; test two interleaved instances (A, B, A, B) produce identical outputs to each instance run alone; test reset/unload then reload.
- **Save-state versioning:** hidden state that is easy to miss `[INF]` from the sources: `prev_interruptible` flag, `D` flag, `I` flag, the pending BUSRQ/BUSAK handshake, System RAM Bus Copy mode, the 20-entry video FIFO contents, sticky collision bits, color-stack pointer, display-enable handshake, PSG divider phases / envelope counter / noise register, controller sample latch, power-on RAM policy. Include profile id and system-image digests in the state header; refuse loading into a different profile; test old-prefix, truncated, oversized, and wrong-profile loads, and that a failed load preserves the running machine (EMULATOR-DNA).
- **Persistence policy:** Battery-backed or Intellicart-like persistence is profile-defined (EMULATOR-DNA); don't add file paths to the core.

**Phase to address:** B (contract, bounds, ownership), E (input boundary), G (state/save).

### Pitfall 18: Process: over-broad first milestone, research-only drift, premature optimization, CI matrix bloat

**What goes wrong:** The first milestone tries to deliver CPU + STIC + PSG + all controllers + all variants + frontends; or the team keeps researching timing questions that cannot be settled without hardware; or optimization starts before correctness baselines; or the CI matrix balloons before there is a failure class to justify it.

**Why it happens in *this* project:** The research record contains many `[UNK]` items (PAL, BUSRQ cycles, visibility windows, controller electricals, EXEC legal status). Each looks like a prerequisite. PROJECT.md already warns about research-only drift and recommends one visible playable/homebrew scenario early. `[SRC PROJECT.md]`

**How to avoid:** `[REC]`
- **Vertical first slice:** one named profile + one project-authored diagnostic + the headless runner + an installed consumer, as PROJECT.md recommends, with CPU/STIC/PSG coverage grown only as far as the slice needs. Anything in Pitfall 7/10 that is `[UNK]` gets a named default policy and a labeled test, not a research task blocking the slice.
- **Time-box unknowns:** each `[UNK]` gets (a) default policy, (b) the observable that would change it, (c) the phase that will revisit. A decision log entry, not an open-ended study.
- **Performance after baselines:** no dispatch tables, JITs, SIMD, or threading until there is a named workload, a correct-output baseline, and a profile that attributes cost (AGENTS.md / PROJECT.md).
- **CI:** one local command == fast PR gate; each CI job maps to a distinct failure class; measure queue/setup/build/test before adding caches or matrix legs. Defer: macOS+Linux+Windows x compilers x profiles, fuzzing, soak and performance distributions until a recurring failure justifies them.
- **Playable scenario:** author a tiny original program (or get rights-cleared homebrew) with a guest-state predicate by the end of the first slice.

**Warning signs:** A phase whose success criteria list more than one chip; no runnable artifact after two phases; a phase with only "document" outputs; a CI file with more than three jobs before the first release; benchmark scripts before a correctness baseline exists.

**Phase to address:** Roadmap shape (before A), enforced at each phase transition.

## Moderate Pitfalls

### Pitfall 19: Using the wiki/community statement of a rule as the spec when it contradicts the primary manual
**What goes wrong:** The intellivision.us wiki page for the CP1610 describes R6 as auto-incrementing on indirect reads and auto-decrementing on indirect writes. `[COMM S1]` The GI manual transcription says the opposite: mode 6 is post-increment for output (push) and pre-decrement for input (pull). `[SRC S12]` The jzIntv interrupt doc agrees with the manual (stack starts at $2F1 and grows upward). `[SRC S8]` An implementer following the wiki gets a stack that grows the wrong way.
**Prevention:** `[REC]` A two-source rule for every requirement: one primary (data sheet, manual, schematic, measurement) plus one corroboration. Log contradictions in a `DISCREPANCIES.md` with both citations; resolve by test on a vector, not by vote.
**Phase:** A (rule), B-E (application).

### Pitfall 20: SDBD double-byte details
**What goes wrong:** SDBD is treated as "read a 16-bit word". The manual says: SDBD must immediately precede the instruction; in indirect modes 4, 5 and 7 two words are read (low byte from the first word's low 8 bits, high byte from the second's low 8), with modes 4 and 5 post-incrementing twice; with modes 1-3 only **one** word is accessed and both bytes come from the same word's low 8 bits; modes 0 and 6 are "not supported". `[SRC S12]` MAME marks mode-110 SDBD `???` and does not support SDBD MVO@/MVOI. `[SRC S18]`
**Prevention:** `[REC]` Test each documented mode plus the "not supported" ones with an explicit **policy** (undefined behavior is decided and named, not accidental). Verify the D flag is cleared after exactly one instruction.
**Phase:** B.

### Pitfall 21: Flags and non-obvious CP1610 behavior
**What goes wrong:** S/Z/O/C flag rules and quirks are implemented from memory. Known source items: C and O double as storage for bits shifted out; in SWAP, SLR, SAR, SARC and RRC the S flag reflects bit 7, not bit 15 (MAME also comments this); TCI pulses an unconnected pin so it is a NOP on Intellivision; HLT halts until STPST transitions; the GI reference is "occasionally incomplete or inaccurate". `[COMM S1][SRC S18]` Conditional branches are listed as 7/9 cycles without saying which is taken. `[COMM S2]`
**Prevention:** `[REC]` One vector per opcode per flag outcome, hand-derived; branch timing (taken vs not-taken) as an explicit `[UNK]` until the manual's cycle column is read per opcode; never infer which of two numbers is "taken".
**Phase:** B.

### Pitfall 22: Treating PAL/SECAM as a flag
**What goes wrong:** PAL is implemented by swapping the clock. Numbers are unmeasured (Pitfall 7), the PSG clock (4.0 MHz) and CPU clock (1.0 MHz) change, scanlines per frame change, and guests with PAL/NTSC detection (IntyBASIC prologue) follow different code paths. `[SRC S8][SRC S9][SRC S21]`
**Prevention:** `[REC]` PAL is a separate profile with `unknown-default-chosen` fields. Do not claim it in the first slice.
**Phase:** G.

### Pitfall 23: Fixture provenance records that do not travel with the artifact
**What goes wrong:** The manifest lists a fixture, but the packaged artifact or the installed consumer includes a different file, or the notice text is missing from the release bundle.
**Prevention:** `[REC]` The installed-consumer test (PROJECT.md) also verifies that the shipped bundle contains exactly the manifest-listed fixtures and notices; fails on extras (including accidentally included system images).
**Phase:** F.

### Pitfall 24: Treating the service manual as an oracle
**What goes wrong:** The 2609 service manual describes MTE-201 diagnostic procedures and a follow-up game check. `[SRC EMULATOR-DNA]` It describes *what a technician does*, not ROM contents or pass criteria that can be automated, and the scan is third-party hosted.
**Prevention:** `[REC]` Use it only to discover diagnostic *categories* (as PROJECT.md says). Author original diagnostics with literal expected outcomes.
**Phase:** A, F.

### Pitfall 25: Debug/inspection surface that perturbs execution
**What goes wrong:** Breakpoints, memory views and register dumps use the CPU read path, flip STIC mode (Pitfall 8), or advance auto-increment registers.
**Prevention:** `[REC]` A separate side-effect-free inspection API with its own tests, and tests proving trace on/off yields identical machine state.
**Phase:** B, D.

## Minor Pitfalls

### Pitfall 26: Mis-specified GROM/GRAM visibility to hosts
Hosts that read GRAM mid-frame get garbage or stale values. **Prevention:** `[REC]` Expose GRAM only through the inspection API at a defined boundary.

### Pitfall 27: Treating keyboard-component, IntelliVoice and ECS as "just config"
They add devices on shared address ranges ($0080-$0081, $00E0-$00F0 region, $01FE-$01FF overlap) and PSG #2. `[SRC S11]` **Prevention:** `[REC]` Out of the first profile; any support is a new named profile with its own evidence.

### Pitfall 28: Time/units confusion in logs and reports
Reports mix cycles, scanlines, frames and wall seconds. **Prevention:** `[REC]` Machine-time unit named in every report header; never report wall-clock as correctness evidence.

### Pitfall 29: Unqualified compatibility claims
"Plays X games" statements, percentages or logos violate the Core Value. **Prevention:** `[REC]` Every claim cites profile id, content identity (digest + rights status), tier, and oracle.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Frame-granular STIC rendering | Simple, fast | Loses row-level BACKTAB/BUSRQ effects; later rewrite of STIC and runner boundary | Only if named in the profile as an approximation with a documented unrepresentable set (Pitfall 9) |
| Hard-coded NTSC constants | Quick start | PAL/variants need a rewrite; conflicts between sources hidden | Never as bare constants; fine as profile data |
| Copying jzIntv/MAME tables | Fast "correct" values | GPL/provenance risk, non-independent oracle | Never without owner-approved license decision |
| Using a generic AY-3-8910 library | Free sound | Wrong register order/envelope select/steps; dependency | Only after a per-rule audit against Pitfall 12; prefer own small module |
| Replacement EXEC without contract tests | Unblocks CI | Evidence bound to non-real EXEC; timing differences | Only with boot-contract tests and profile-tagged claims |
| Golden updated by `--update` flag | Fast green | Stale/false evidence | Never without tier + diff review |
| Skip-on-missing-fixture | Passes for contributors without images | Skipped green hides coverage loss | Only for optional-tier tests with counted, visible skips |
| Wall-clock pacing in the core | Easy realtime | Non-determinism, untestable | Never; pacing belongs to the host |
| Debugger uses CPU read path | Simple | Side effects (mode switch, auto-increment) | Never |
| Float audio mixing in the core output | Simple | Platform-dependent hashes | Only outside the evidence path |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| LibFuturo candidate (32-bit mask, single content span + config id) `[SRC PROJECT.md]` | Assuming keypad + disc + two players fit as one-hot bits; assuming content + EXEC + GROM fit in a single span | Check electrical encoding (2 x 8 bits fits) `[INF]`; decide how system images are supplied; prove with a real consumer before proposing any shared-contract change |
| Host controller mapping | Letting the host send any key/disc combination | Host layer maps to realizable electrical states; core refuses or AND-merges per documented policy |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Per-instruction bus-request/interrupt polling written naively | Slow main loop | Keep correctness first; optimize only after a named workload and baseline exist | When benchmark workloads exist; not before |
| Per-scanline STIC simulation with allocation | GC/alloc churn | Preallocate; measure | Row-granular STIC at ~262 lines/frame, ~60 fps |

| CI matrix expansion | Long PR times | Measure queue/setup/build/test first (AGENTS.md) | When >3 required jobs |
| "Performance" tests mixing correctness | Flaky and unattributable | Separate throughput, latency and CI-time measures (EMULATOR-DNA) | When benchmarks arrive |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|

| Save-state load without version/profile/size checks | Memory corruption, wrong-profile load | Header with version, profile id, size; bounded parse; refuse on mismatch |
| Echoing user-supplied system-image paths or digests in logs/CI artifacts | Leaks rights-bearing material locations | Redact; never upload |
| Caching system images in CI | Redistribution without permission | Secrets-style mount only; artifact denylist test |
| Using a GPL dependency/transitive code accidentally | License obligations | Dependency license check in CI as a distinct failure class |
| Debug/trace output containing guest memory dumps of a commercial ROM | Redistribution of content | Do not publish traces of third-party content |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| No overlay equivalent for keypad | Players cannot know which key is which | Overlay *metadata* only if a user need is shown (EMULATOR-DNA); host feature, not core |
| Disc direction mapped to 4-way arrows only | 16-direction games unplayable | Host maps to 16 directions; core accepts electrical state |
| Silent refusal | User sees blank screen | Specific refusal reason: unsupported profile, missing system image, malformed content |
| Compatibility labels without profile | Misleading expectations | Always state exact profile + content identity |
| Hard-coded 4:3 or pixel-perfect only | Wrong aspect on host | Host layer chooses aspect from profile metadata |

## "Looks Done But Isn't" Checklist

- [ ] **CPU "complete":** Often missing SDBD edge modes, interruptibility of every opcode, EIS/DIS one-instruction delay, stack direction. Verify the hand-written vector list, with a failing named-fault control for each.
- [ ] **STIC "renders title screen":** Often missing out-of-window access policy, read side effects at $0021, sticky collisions, delay/border extension, 159-column rule, display-enable handshake. Verify each with a diagnostic.
- [ ] **PSG "has sound":** Often missing 2-bit envelope select, correct register order, noise LFSR, envelope step rule. Verify against hand-derived vectors, not by ear.
- [ ] **Controllers "work":** Often missing ambiguous-combination behavior, right/left port mapping, direction bits. Verify two-controller AND-merge tests.
- [ ] **Cartridge loading "works":** Often missing refusal tests and 10-bit handling. Verify the malformed-content list.
- [ ] **Green CI:** Often missing a count of skipped/missing tests. Verify the inventory gate and the stale-output check.
- [ ] **Fixture "cleared":** Often only a digest recorded. Verify the `redistributable` column and license text.
- [ ] **Installed consumer:** Often runs from the source tree. Verify clean install, package contents and notices.
- [ ] **Deterministic:** Often only checked by running twice. Verify with a second instance, a different host, and no wall-clock or uninitialized-memory dependence (power-on RAM policy fixed).
- [ ] **Save states:** Often missing hidden state (Pitfall 17 list) and version refusal. Verify save/load mid-frame, mid-SDBD, mid-BUSRQ.
- [ ] **"Playable":** Often only a title screen. Verify a guest-state predicate.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Core-vs-self goldens found to encode a bug | MEDIUM | Tag all goldens with tier; regenerate only after an independent expected value exists; add the negative control |
| GPL code or tables copied | HIGH | Identify and isolate, rewrite from primary source by someone who has not read the code, document provenance; owner decision on license |
| System image/ROM committed or cached | HIGH | Rewrite history and purge caches/artifacts with owner awareness; add denylist test; owner gate on disclosure |
| Per-frame STIC renderer insufficient | HIGH | Introduce row/scanline model behind the same raw-framebuffer boundary; keep per-frame as an optional approximation profile |
| Wrong PSG chip model | MEDIUM | Replace the module behind the raw-audio boundary; goldens regenerated from hand-derived vectors |
| Controller model too logical | MEDIUM | Add an electrical layer; keep logical mapping as a host-side adapter |
| Skipped tests hid a regression | MEDIUM | Add inventory gate; run the full set once; fix |
| Name/trademark conflict | MEDIUM-HIGH | Rename early; owner gate before any publication |
| Save-state format missing hidden state | MEDIUM | Version bump with refusal for old states; add state coverage tests |
